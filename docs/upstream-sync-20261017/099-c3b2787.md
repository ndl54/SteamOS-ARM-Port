## Findings and scoped repairs

The original `down()` filters the area's `touchPoints` property, which was empty because no objects were declared. The source correctly supplies three objects. [Qt's MultiPointTouchArea documentation](https://doc.qt.io/qt-6/qml-qtquick-multipointtoucharea.html) distinguishes this user-defined list from signal arguments and documents its empty default. We retain that source addition without changing mouseEnabled, min/max points, routes or button names.

Enabling the pad exposes existing gesture-state defects in the same component. The following corrections were reproduced with actual extracted QML JavaScript and synthetic points before repair:

1. **Finger-count changes generated false motion.** Removing a third finger left the old three-finger centroid as the next two-finger origin, producing wheel output even with stationary remaining fingers. Adding a distant second finger could likewise scroll and mark a tap as travelled. [Qt v6.10.0 implementation](https://raw.githubusercontent.com/qt/qtdeclarative/v6.10.0/src/quick/items/qquickmultipointtoucharea.cpp) updates point properties before callbacks, emits released before updated and updated before pressed, and includes stationary points in updated. Track the current count separately from maximum count, rebase centroid/spread on count changes, and rebase the tap/slop origin while still stationary. This suppresses count-change motion; movement in the same sample can be intentionally discarded. Maximum count still chooses right/middle tap and prevents a multi-finger gesture from becoming one-finger pointer movement.
2. **Changing Touchpad to Keyboard left pending work alive.** Main keeps RemotePad visible for both pages; the component's old root visibility hook therefore cannot cancel the delayed tap or scrolling momentum on a mode switch. Add cleanup when the pad surface hides while RemotePad remains visible. Retain the original root visibility cleanup for leaving either page. `letGo()` now clears maximum/current counts, fine/strip/travel flags, pending deltas, momentum, pending click and drag state. It sends left-up for a locally held drag and the existing release-all endpoint. Canceled input uses that same cleanup. Updated/released callbacks with no active gesture return, preventing synthetic late callbacks from reviving motion/clicks. The latter is defensive sequence coverage, not evidence that every Qt backend delivers late events.
3. **Symmetric pinch never reached the pinch code.** The original travel gate only measured centroid movement, so spreading two fingers symmetrically did nothing. Crossing the existing 50-scaled-pixel pinch threshold also marks the gesture travelled, allowing the existing Ctrl+=/Ctrl+- chord path. No new gesture, threshold, keyboard mapping or zoom transport is introduced.

The first original-source regression run passed six cases and failed four transition/cleanup cases. Extending event-order coverage reproduced an additional add-finger failure, including the following stationary sample, and a symmetric-pinch failure. All are corrected. The source parent also fails the declared-point test (0 tracked fingers instead of 1). One intermediate harness run failed because the extractor required a braced onCanceled handler; retaining the existing braced style fixed that harness mismatch, not a Qt syntax problem.

## Input, coordinate, transport and lifecycle trace

Main instantiates one persistent RemotePad, selecting pad/keys by page. MultiPointTouchArea reads pressed slots, averages local x/y, and uses scaled slop. The global scale is `min(window.width/1240, window.height/1080)`. Pointer motion divides by Ui.s and applies configured speed (default 1.6), sample-distance acceleration capped at 3x, and 0.33 Precise gain. A 16 ms timer rounds accumulated relative deltas and retains/clears fractions. This is relative input, not absolute mapping to the top-panel resolution; compositor acceleration and event-rate dependence remain.

A quick single tap starts a 220 ms click timer; a second quick tap generates two clicks, while a second stroke past slop holds left until the last finger lifts. Maximum simultaneous finger count selects right/middle tap. The right strip and two-finger scrolling accumulate wheel notches at 40 scaled pixels per step, with optional natural sign inversion and 0.92-per-tick momentum decay. Three-finger horizontal movement produces Alt+Tab chords per 120 scaled pixels. The separate keyboard mini-pad retains its existing DragHandler, direct relative delta sends and TapHandler; its code is unchanged. Held Left/Right/Precise controls retain their PointHandler activation/deactivation behavior and source095 contrast binding.

`Ui.send` calls the existing asynchronous XMLHttpRequest POST path, with JSON and X-Token; it does not request state refresh or inspect the response. The dashboard binds ThreadingHTTPServer to loopback on an ephemeral port, generates a per-run random token and writes API credentials through an os.open mode-0600 runtime file. Handler checks the token before dispatching `/remote/move`, `/wheel`, `/click`, `/type` and `/letgo`. Input quantities are converted to int; RemoteInput's lock serializes each method once entered. Move emits REL_X/Y clamped to +/-2000; wheel clamps to +/-20 with vertical sign inversion; button emits EV_KEY down/up; release sends up for all three mouse buttons and four modifiers. UInputDevice appends SYN_REPORT. No backend/protocol/permission change was made.

Virtual mouse/keyboard devices are created lazily through `/dev/uinput` as the session user, with existing names/product IDs. The source tree inspected does not establish the installed image's actual uinput ACL/group access; no new permissive rule was added. Open failures return false and log; the fire-and-forget UI does not surface that failure. This remains a runtime prerequisite, not proof that devices can be created.

Game Mode's bottom session requires bottom-screen.env, generated only when enabled with a distinct second connector. It sets GAMESCOPE_INPUT_ONLY to the bottom touchscreen selector (or `none`). Gamescope's wlserver_new_input exclusion runs for all input types, so the new virtual device names do not pass that bottom-panel whitelist; the main compositor can consume them. Desktop autostart requires two connected DSI panels and respects disabled settings/boot flag; KWin consumes the virtual devices on the shared desktop, so top-only pointer targeting in Desktop Mode is not enforced by this QML. Normal single-panel EVO does not gain a bottom session through this change; explicit external-output configuration remains supported by existing logic. Full overlay copy plus QML 0644 staging already carries this file.
