## Semantic repairs and review

### LPASS macro votes

Retained macro/dcodec acquisition before inner runtime-resume clocks and release after inner runtime-suspend clocks, with reverse-order unwind if either outer vote or inner clock setup fails. Found that the old remove functions unconditionally dropped clocks that can now already be runtime-suspended; they now drain/disable runtime PM and only release owned active votes. PM enablement moves after the remaining fallible probe clock-output registration, so a failed probe cannot leave enabled PM callbacks alongside unwound clocks. The output clock callbacks and provider registration were inspected; no new register programming is introduced there.

The old inner resume functions ignored `regcache_sync` failures. They now return the error, restore cache-only/dirty state and unwind their acquired clocks; the new wrappers then release dcodec/macro. VA retains its conditional NPL handling. All three copies have identical patch contents except kernel line offsets.

### DSI iface ownership and errors

The assigned patch directly unprepared a clock also owned by `pm_clk`, using a second handle. It also cleared its unprepared flag before checking resume prepare success. Inspected `drivers/base/power/clock_ops.c`: `pm_clk` separately tracks prepared/acquired states, treats prepare-only clocks differently, and unprepares its owned count on destruction. Borrowing that count can leave stale framework state or unbalance teardown/repeated failures.

The repaired patch explicitly owns one iface clock reference and its prepared/enabled state. It retains the source policy: drop the prepare during system sleep only when runtime-suspended, restore only a vote actually dropped by that sleep, and leave active PHYs alone. It preserves the prepare-only clock behavior using `clk_is_enabled_when_prepared`. Successful operations alone set state; failed system prepare stays retryable, and runtime resume prepares before enabling. Devres drains runtime PM before the clock cleanup and only releases votes still owned. Explicit `linux/clk.h` declarations are included. The source's noirq sleep phase remains, requiring eventual platform validation.

### Battery notifications and request serialization

`qcom_battmgr_request` shares one completion/error field; callers must hold `battmgr->lock`. The new prepare/complete requests did not. Added locking around both and around the existing service-up enable worker. A lock-protected sleep flag prevents that worker from re-enabling notifications after prepare. Service transitions use WRITE_ONCE and the new callbacks use READ_ONCE. The flag is cleared in complete, including aborted suspend; battery/USB change notifications remain outside the lock. The existing one-second request timeout and best-effort suspend behavior remain: a firmware error is reported, not claimed as successful notification suppression. No RTC ownership or wake-cause policy changes.

### Wake-key lifecycle

The source shared unsynchronized sleeping/deadline globals among power/reset-key devices. It also dropped a release for a press already reported before suspend, which can leave the input key stuck, and could synthesize a fresh press from a delayed release.

Each key now owns its sleeping/deadline state protected by a mutex shared by its threaded IRQ and PM callbacks (the pinned driver requests a threaded IRQ with IRQF_ONESHOT). Suspend reports a balancing release, remembers any held key and suppresses an initial release-only wake event. Resume starts that device's three-second window. An ignored held press is consumed through its eventual release, even after the window; an ordinary new press outside the window clears release suppression. The three-second suppression policy still intentionally ignores a deliberate second press during display recovery. Existing debounce and hardware-reset setup remain; this is not proof of real IRQ timing.

### WSA884x recovery

The source's READ_ONCE check followed by register writes can race with mute, its nonsynchronous cancellation can overlap a restart, and its cleanup action was registered before the regmap/regulators it uses (devres releases in reverse order).

- A dedicated PA mutex serializes the complete worker/restart sequence with mute/unmute and the unmute timestamp/check counter.
- Mute cancels queued work under the state lock; an in-flight worker finishes before mute clears the PA. Stream free and DAPM pre-power-down also stop/drain recovery.
- A freezable queue prevents periodic recovery from running during system device suspend. Runtime-active acquisition is still conditional and paired with put; it never actively wakes an idle codec to poll.
- Cleanup is registered after regmap initialization and PM enable, before component registration. Component teardown precedes cancellation, then the action drains work and disables runtime PM before regmap/reset/regulator resources disappear. Action-registration failure uses the same cleanup.
- Recovery is narrowed to the source's observed signature: ERR_COND0 bit 6 alone, ERR_COND1 zero, and PA_ON_ERR interrupt bit 1. Other signatures are not automatically reset. Only that interrupt bit is cleared; writes are checked, and a failed step does not proceed to re-enable the amplifier. This deliberately does not claim recovery for every silent-speaker cause.
- Existing volatile status-register classifications, SoundWire stream removal, Pocket S2 compander/gain condition and user volume paths remain. No new WSA884x patch is applied to SM8750; 078 Elite gain is still a separate final-review issue.

### Fan, LEDs and USB

The ordinary SM8550/SM8750 fan patch now attempts awake-PWM restoration on failure. The SM8650 charging-aware variant, also inherited by TB321FU, cuts the supply in its charging-off branch as well as ordinary suspend, preserves charging-on operation, and restores the awake state when suspend fails. Regulator/PWM failures still propagate; recovery itself is best effort.

HTR3212 now serializes shutdown/reinitialization with brightness writes using a separate lifecycle mutex. While suspended, LED requests stay in the LED core's desired brightness rather than issuing I2C to a shut-down chip. Resume restores brightness with checked errors; failure keeps the driver marked suspended. The underlying register mutex remains separate to avoid recursive locking. This is a compatible-specific HTR3212 change, not an EVO Android LED-protocol change.

All three DWC3/xHCI patches remain byte-identical to the assigned source. Eight property slots cover seven possible entries plus the zero terminator. Platform-device error cleanup and property lifetime remain intact. The reset quirk reinitializes xHCI across resume and resets attached devices; the pinned xHCI core also holds a runtime-PM reference while a device is attached for this quirk. That reliability/power tradeoff is recorded, not hidden. No claim that USB storage connections or data integrity were tested.
