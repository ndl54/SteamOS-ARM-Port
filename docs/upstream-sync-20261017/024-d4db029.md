## Findings and resolutions

The source adds one udev rule matching `SUBSYSTEM=="backlight"` and exact `KERNEL=="aw99706-backlight"`. It queues `chgrp video` then `chmod g+w` for `/sys/class/backlight/%k/brightness`. It does not grant world-write, change the owning user, recursively change permissions, or open `bl_power`, max/actual brightness, raw I2C or unrelated sysfs attributes.

Two narrow integration repairs were made:

1. Add `ACTION=="add|change"`. Coldplug/add and later brightness/change events retain the permission repair; remove/bind/unbind do not queue commands against a missing or irrelevant attribute. The commands are idempotent, although every matched change still queues two processes.
2. Explicitly stage the rule as mode 0644 in `scripts/install-elden.sh`. SM8750 staging copies selected files from `steamos-overlay`, not the whole rules directory. Its Gamescope scripts copy goes to `/usr/share/gamescope` and `/usr/local/share/gamescope`, which are not udev rule directories. Without this repair, simply adding the source file does not install the new rule through the reviewed Elden pipeline. The existing `*-elden-steamos` extra-kernel guard calls this installer, and failures already propagate. No installer was executed during this review.

The general SM8550/SM8650 path (`scripts/apply-overlays.sh`) already explicitly installs `external-and-mods/gamescope/scripts/udev/60-gamescope-backlight.rules` into the udev rules directory. That existing rule grants video-group writes to brightness and bl_power for all backlights on add/change. The EVO display installer also installs it. Both paths and that existing rule remain unchanged. The new narrow rule is redundant where the general rule is present, but matters for the reviewed SM8750/Elden staging path and does not require replacing its Gamescope binary.

## Users, ordering and write path

Gamescope runs in the existing user session; the session wrapper execs it without switching user. The reviewed scripts identify the image user as steamos (home ownership 1000:1000). These changes neither create `video` nor add users to it. Correct group existence and supplementary membership are inherited from the base image and must be verified on the eventual image/device; no current target group database or process credentials were read here. CAP_SYS_NICE is unrelated to this file-write permission.

Udev runs the queued commands with its system privileges. `chgrp video` precedes `chmod g+w` in the rule. Lexically, 60-gamescope precedes 99-steamos-arm-tablet-backlight; their brightness operations agree where both exist. The separate 99-zz-steamos-arm-backlight-untag rule, where installed, removes the systemd tag without cancelling RUN commands or these permissions. No new service, systemd device dependency, udev-settle wait, or login ordering was added. The Elden firmware unit's existing ordering before display-manager does not prove this particular backlight event has completed.

Vendored Gamescope calls `InitBacklight` during startup, chooses an explicit env/convar path or a sysfs device with a valid max_brightness (preferring raw/platform), and opens its brightness file O_RDWR, falling back to O_WRONLY. Its internal permission relaxation runs only as root, so user Gamescope depends on the udev/group setup. The Steam internal-display brightness property enters `ApplySteamBrightnessValue`, normalizes/clamps it and writes through the retained fd; brightness keys enter the same setter. The code seeks to zero before writing and can reopen after a seek failure. No hardware-open retry is performed when initialization had no usable fd, so a late device/permission event can leave that session using software fallback until restart. This pre-existing timing limitation is recorded, not expanded into an unrelated Gamescope change.
