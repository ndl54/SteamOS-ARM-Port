## Findings and resolutions

### Broad upstream recognition could destroy user layouts

The source assumes that any unstamped file whose outputs all have Rotated270 must be an old generated seed if current panels need a different orientation. This is not sufficient evidence: a user may keep that rotation while changing position, scale, refresh rate, brightness, color settings, enabled state, or saved docked outputs. The source then replaces the entire layout and can discard those choices.

Reproduced against the exact source helper using temporary files: a Rotated270 layout with brightness 0.4 and position x=100 was accepted and overwritten. The final recognizer rejects it.

The repair now requires all of:

- No desktop-outputs ownership stamp, including no empty/stale stamp.
- Exactly one currently discovered panel, DSI-1, explicitly reported left-up.
- One of the affected model names: Retroid Pocket 6, AYN Odin 2 Portal, AYANEO Pocket EVO, Pocket DMG or Pocket DS.
- An exact desktop-fit-1 marker matching the current connector/dimensions and the original producer's scale formula.
- The entire parsed layout matches the staged legacy layout with exactly the producer's scale and autoRotation changes. Formatting/object key order may differ; other fields, additional sections, outputs or setups may not.

Missing/unreadable/invalid metadata or malformed JSON is not treated as proof of an old seed. Unknown boards, missing orientation, different connectors and multi-panel configurations are preserved. Pocket DS can qualify only when exactly one panel is discovered and the marker matches; desktop-fit never generated the claimed two-panel scaled seed, so its ordinary dual-panel layout is deliberately excluded.

### Migration also lost the completed desktop-fit policy

The upstream repair rebuilds at desktop-outputs' 1.25 scale and InTabletMode policy. The existing desktop-fit-1 marker prevents fitting again. Reproduced this against source: a 1.5/Never old seed became 1.25/InTabletMode.

For a verified seed, the final repair builds the current panel's layout/60-Hz preference, then retains the desktop-fit scale and Never policy. It does not create a desktop-outputs ownership stamp: otherwise the next startup would regenerate the unfitted defaults. The repaired Rotated90 layout cannot match the old Rotated270 seed, so subsequent starts preserve it, just as they preserve a layout changed by desktop-fit. The desktop-fit marker is retained byte-for-byte; no kwinrc setting, touch matrix or user file other than this verified output layout is changed by the migration.

The pre-existing missing-file, exact legacy digest and matching ownership-stamp paths retain their existing generation behavior, including managed dual-screen touch routing.

### Atomic replacement and failures

Config and ownership-stamp writes now use unique temporary files in the destination directory, followed by `os.replace`, with temporary-file cleanup on failure. This avoids the shared `.tmp` filename and avoids truncating an existing stamp. New temp files use private per-user permissions. The migration itself replaces just one config and never mutates its marker or touch mapping.

Injected partial-write/disk-full and replace failures leave the old migration input unchanged and clean up temporary files; retry then succeeds. A separate stamp-replace failure on the ordinary generation path leaves a complete new config and the old complete stamp. Subsequent runs conservatively preserve the unrecognized config rather than guessing ownership. The existing top-level exception guard still logs failure and lets Plasma start.

## Remaining limits

This is source review plus local synthetic evidence, not device/runtime evidence. Real KWin normalization, actual model strings/DRM orientation, screen rotation, scaling, touch/pen alignment and session behavior require later image/device validation. A real config that KWin normalized beyond the known seed, a missing/stale marker, an unknown model or changed panel mode is intentionally left alone. A user-created layout indistinguishable in every compared value and marker from the original seed cannot be distinguished historically; the implementation makes no claim that a rotation alone proves provenance.

Per-file rename is atomic visibility, not an fsync-backed power-loss transaction. Config, stamp and existing multi-panel touch updates are not a single transaction; concurrent writers are not locked. Existing general `map_touch` behavior is outside this repair, and only synthetic routing was checked. Repairs deliberately cease ownership after migration, so future topology changes rely on KWin/user settings as other fitted layouts already do.

No build script, kernel/Gamescope/InputPlumber/rootfs/image/package compilation, VM/container start, mount, install, flash, deployment, service action, live display command/config change, device action or real-log upload was performed. Build validation remains deferred until completion of all 109 source reviews.
