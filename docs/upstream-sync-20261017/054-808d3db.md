## Findings and resolutions

1. **Never fall back to an ungated manifest.** The source copied raw JSON on parsing/write failure and accepted any `.so`/`.json` archive member. The repair requires the pinned archive hash, exact library/manifest members, expected x86-64 ELF header and library reference; it publishes only the renamed library and validated Classic-gated manifest. There is no raw-copy fallback. Library publication precedes the gated manifest. Missing/corrupt artifacts return an error; ARM64 additionally requires its image library/manifest. Installed status requires runtime files, a valid config, manifest isolation and an executable launch script. No automatic fallback to v2 is introduced.
2. **Keep saved configuration and launcher semantics.** Reinstallation previously rewrote user config, reset no_fp16=false, potentially replaced the chosen DLL, and regenerated the launcher from defaults instead of the selected profile. Reinstall now validates but preserves exact existing config bytes, then generates the wrapper from that profile, including script workarounds. A strict TOML parser rejects malformed/unsupported versions, sections/fields and duplicate profile names instead of silently manufacturing defaults. Normal UI edits preserve supported profiles, quoted DLL/name strings and global no_fp16. Configuration field types/ranges are validated; profile names are shell-quoted. Unsupported custom schemas are preserved with an error and need manual adjustment before UI editing.
3. **Surface publication failures and protect user launchers.** Config/script writes use unique same-directory temporary files and atomic replacement. A launcher-write failure returns failure instead of a success toast. New wrappers have an ownership marker; the known source054 generated wrappers are also recognized. Install/update/uninstall refuse an unrelated or symlinked launcher. Uninstall preserves Classic config and never migrates/moves the v2 plugin's legacy settings. Config and wrapper are separate publications: if config succeeds and the wrapper fails, the saved config can be newer than the launcher; the error is visible and retry is required.
4. **Handle mixed wrappers without stacking 1.x and 2.0.** V2's workaround wrapper clears DISABLE_LSFGVK for a matching AppID. Nested after Classic, the source could thereby leave Classic enabled while re-enabling v2. Added LSFG_CLASSIC to that same managed-environment cleanup. Both nesting orders now select only one layer in the tested matching-AppID scenarios; users should still use just one wrapper. V2's startup repair already regenerates its owned wrapper from saved state. Existing unmanaged wrappers and external manual environment/manifest changes are outside this guarantee.
5. **Block unsafe Classic Flatpak actions.** The inherited Classic bundles and service use the same `org.freedesktop.Platform.VulkanLayer.lsfgvk/x86_64/<branch>` IDs as v2. Its uninstall can remove v2 and its override removal uses a blanket `--reset`. Those bundles are not independently renamed/gated Classic runtimes. Classic Flatpak service operations now return a clear unsupported error without spawning commands; plugin removal no longer touches those extensions. The shipped UI presents the limitation instead of setup controls. Bundled Flatpak binaries remain unchanged for provenance, but are not installed through Classic. Use the existing v2 plugin for Flatpak; isolated Classic Flatpak packaging is deferred.
6. **Preserve user plugin copies during bundled updates.** The source deleted an existing plugin (even a newer/custom one), deleted a fixed `.new` path, ignored chown failures and could crash on non-object state/package JSON. The installer now validates metadata, fingerprints ordinary bundle files/modes (ignoring generated `__pycache__`), installs missing copies, adopts an exact matching copy, and updates only a previously recorded unchanged copy. Custom/newer/unmanaged or symlinked copies are preserved. Each offered version is remembered; removal remains respected until a new bundle version arrives. Unique staging plus rename backup keeps the old tree during copy/chown/publication/state errors; failed restoration retains recovery data. Corrupt state fails closed rather than resetting history. Bundle failures are reported, return nonzero and do not prevent the pre-existing SteamGridDB text fix from being attempted. The repaired bundle identifies itself as `0.12.2+steamos.1`.
7. **Keep backend and shipped UI aligned.** Corrected Classic config-path and manual-profile instructions, isolated its UI collapse keys, removed the unused frontend manager calls to nonexistent `get_configuration`/`reset_configuration`, and replaced its Flatpak modal with the explicit availability message. All remaining callable names map to Plugin methods, manifest names match plugin.json, and frontend defaults match shared_config.py. This snapshot has no frontend source tree; `dist/index.js` was edited directly and syntax/contract checked, never rebuilt or rendered. Trailing whitespace in newly added text was normalized.

Native ARM64/x86 library dependencies, loader treatment of mixed-architecture manifests, sandbox visibility of HOME layers/config, Lossless.dll compatibility with the user's installed Steam branch and actual Decky RPC/rendering require image/runtime validation later. The Classic binary archive is x86-64 only; this review does not establish a separate native 32-bit layer. Default Classic WSI-off behavior may disable Steam's limiter. The ARM64 guard verifies presence/manifest isolation, not full ELF dependency resolution. Installed status is not proof of an available compatible DLL or active generated frames.

Config/launcher/library/manifest publication is per file, not one crash-atomic transaction. Disk or process failure may leave a partial installation requiring retry, which must not be described as successfully running. The bundled installer keeps ordinary rollback data through handled failures, but sudden power loss between directory renames, concurrent user edits, filesystem labels/ACLs, real chown and Decky's watcher/restart ordering remain untested. A modified/unmanaged plugin is deliberately retained rather than upgraded; old history without a fingerprint does not authorize overwriting it. No comprehensive hostile/concurrent HOME-tree audit is claimed.

Classic Flatpak support is intentionally unavailable until truly isolated bundles exist. Existing manually installed/shared Flatpak state is left alone. Unknown custom config sections/fields are preserved but rejected for editing. Classic profiles are manual/global selections; v2 and dashboard profiles remain independent. Direct dist edits need to be retained if a future source/bundle regeneration replaces this snapshot. The separate post-109 build/validation stage remains responsible for compiled image validation; physical-device testing is still separate.
