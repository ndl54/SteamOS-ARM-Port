## Fork overlap and resolutions

### GPU: apply the same fix once

Source adds one combined patch to each of SM8250/8550/8650/8750. On EVO its SM8550 copy would run before the already-present 9053/9054/9055 triple. A temporary targeted reconstruction reproduced the resulting failure at 9053; this was a semantic overlap invisible to Git merge.

Added the exact new combined GPU basename to **EVO-only** PATCH_SKIP. Retained 9053 (only clear CM3_FAULT), 9054 (2-second fault-completion waits in both GMU OOB and HFI), and 9055 (mask GMU2HOST interrupts before boot). Existing old-name skip entries remain, as do 9033/9034 and 9056. After applying the repaired selection, the complete resulting a6xx_gmu.c and a6xx_hfi.c for EVO and shared SM8550 are equal after comments/whitespace removal, not merely similar filenames.

Reviewed the actual poll, completion and error paths: the IRQ leaves MSGQ/OOB response bits for their serialized waiters, early mask precedes GMU boot/HFI start, and the later mask still unmasks CM3 fault. The recovery worker takes gpu->lock; bounded waits remove the particular lock-dependent indefinite completion wait. Poll failure remains an error, OOB acknowledge clearing still occurs, and HFI returns -ETIMEDOUT. This does not guarantee successful recovery or a two-second total limit across all fault/retry activity.

### Vblank: keep configured counter wrap and propagate failure

EVO's 9066 already selected the INTF tear counter and command-mode position path. Added the exact new shared vblank basename to EVO-only PATCH_SKIP and retained/amended 9066. Other SoCs retain the new source patches, with the same repairs.

Content comparison found a real difference: the source used `0xffff - init` on wrap, whereas EVO used `height - init`. The pinned command encoder programs sync_cfg_height=`mode->vtotal * 2` and vsync_init_val=`mode->vdisplay`; this is not a fixed 0xffff period. Kept the fork's configured-height arithmetic and applied it to the new copies and the older pingpong counterpart used when has_intf_te is false. Video-mode INTF_LINE_COUNT and video porch conversion remain unchanged.

Both tear-counter helpers now reject height <= init with the existing unsigned 0xffff invalid sentinel. The command encoder translates that sentinel to -EINVAL on **both** INTF and pingpong paths. Missing master/get_line_count in the virtual encoder returns -EINVAL instead of a fabricated zero. The CRTC takes etime after the read, rejects negative results, sets hpos=0 and uses the command count directly; video mode retains its existing conversion. Read the DRM timestamp consumer: it subtracts the line-derived duration from etime, making an erroneous ~64K wrapped count material to event timestamps. No register or counter behavior was measured; wrap convention, TE loss and physical pacing still need device tests.

EVO order is shared display fixes/flip ordering, then GPU 9053–9055, LUTDMA 9061, repaired 9066, existing plane-color 9070 and EVO panel 9073. Targeted reconstruction includes the later color/panel consumers. The EVO five-mode ICNA3512 descriptor, brightness curve and exact panel compatible remain untouched.

### SN3112 PM correctness

Accepted release/reacquire of the driver's regulator vote and restore of cached channel enables/values under its existing mutex. Reconstructed the driver created by pinned ROCKNIX 0054_sn3112-pwm-driver.patch and inspected probe/apply/remove plus new PM callbacks.

Repaired concrete issues in the new patch:

- `powered` was declared under CONFIG_GPIOLIB but used unconditionally; it is now unconditional. GPIOLIB happens to be enabled in the current pinned config, but the driver Kconfig only depends on I2C.
- Probe now rejects any error GPIO descriptor, not just -EPROBE_DEFER, before the new PM callbacks can dereference it. GPIO operations use the sleepable accessor in these sleepable paths.
- Updates while the rail is unpowered cache channel state without I2C access; resume writes it back.
- Resume only acquires a regulator vote if it does not already own one, but retries register restoration even after a previous powered restore failed. Suspend keeps ownership on regulator-disable failure and restores the shutdown GPIO. Remove only releases an owned vote.

The five-attempt write loop still reports its error. Existing ordinary apply register-error suppression and remove-time I2C writes are pre-existing limitations, not repaired wholesale here. Device PM dependency ordering and real regulator/I2C behavior remain unverified.

### RP6 / ICNA3520 calibration correctness

Accepted RP6's missing F0 page-select correction followed by calibration, and SM8750's ICNA3520 calibration. RP6 0057 must precede 0058; both apply after EVO's rebased RP6 driver as well. SM8750 0040 applies after its existing brightness cap patch. The ICNA3520 interface is descriptor-gated; it does not add calibration to EVO's ICNA3512.

The source exposed sysfs writes that changed DSI pages and mode_flags without serializing against panel prepare/disable/unprepare or backlight I/O. Added a per-panel mutex, initialized before interface registration; prepare/enable/disable/unprepare, calibration show/store and DSI brightness access share it. Scoped mutex guards cover early returns; support was checked in the pinned Linux mutex/cleanup definitions. Init sequences call the internal calibration helper under the prepare lock, not a recursively locking public store. Remove clears enabled under the same lock before detach, so remaining managed attribute accesses only cache values.

Calibration and brightness restore the **original** mode_flags on success/error rather than blindly setting LPM. Calibration attempts the normal-page command even if its preceding transfer failed and returns the first error (or cleanup error). Off-panel / inactive-rate writes remain cached for later preparation. Bounds/defaults and protocol payloads are unchanged. Cached desired calibration survives a transfer error for the next prepare; hardware may still require recovery after a DSI failure. No application caller of these sysfs attribute names exists in the repository outside the patches.

### SSBS and board power/RTC deltas

SM8750 signal patch remains source-identical. Read Linux 7.2 signal restore and spectre_v4_enable_task_mitigation: it updates saved task PSTATE from mitigation mode/TIF_SSBD after valid_user_regs, preserving requested mitigation policy; ssbs_sigreturn=0 keeps the prior behavior. This is source reasoning, not evidence of Wine behavior or a measured Proton speedup. It is not inherited by EVO.

Accepted the three DTS append deltas unchanged. Odin 2 l12b is its panel/touch IO supply; Odin 3's four named regulators match the pinned Wi-Fi power-unit supplies. No conflicting off-in-suspend property was found on those named nodes in the inspected stack. SM8650 RTC uses offset cell `0xbc/4` on pmk8550_sdam_2 and removes UEFI fallback. Pinned rtc-pm8xxx reads/writes the four-byte NVMEM offset, defers small changes and flushes dirty offset at shutdown; the new cell follows the existing SM8550 convention. These are DT/source candidates, not measured power, retention, Android compatibility or clock persistence.
