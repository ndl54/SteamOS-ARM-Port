## Independent scan review

**Gate and bands.** Requires WCN7860 HW20, exactly one exposed base radio and one logical radio, single_pdev_only, and preferred DBS_OR_SBS. ROCKNIX's WCN7860 hardware definition sets single_pdev_only; the WMI capability parser folds physical capabilities into one exposed pdev. The gate still depends on actual firmware reports. It considers only PHY IDs0/1 with matching hardware mode and5GHz capability, requires nonzero increasing ranges and unequal upper bounds, and accepts the smaller upper bound only above both lower bounds and below5925MHz. Invalid/missing/equal/nonoverlapping boundary shapes fall back to ordinary scanning. No invented firmware ranges or regulatory permissions.

Batch classes separate frequencies below3000MHz, lower5GHz through the inclusive boundary, upper5GHz below5925MHz, and6GHz. Batches are consecutive runs in the requested channel order; no sorting, channel insertion or loss is introduced. A single-class unassociated request keeps the ordinary path. An associated selected scan vif uses one-channel batches whenever the gate succeeds. This is based on `arvif->is_up`, not proof that every possible multi-interface association topology is covered. ROC does not allocate a range request and retains its normal path.

**Ownership and errors.** The channel-flex allocation and separately copied IE become range_req; the local pointer is nulled. Each temporary batch copies the fixed request fields and its channel slice, borrows the owned IE, and is freed after synchronous WMI serialization into an skb. The owner frees the IE/request after normal final completion, failed first/later start, scan setup unwind, stop or interface teardown. range_req publication/removal and event state changes use data_lock; allocating/freeing, sleeps and queue control run under the wiphy mutex. Free resumes only a scan-owned TX pause before clearing the owner pointer, so the rest-time dereference has an owner. Repeated cleanup sees a null owner.

**Events and completion.** Successful intermediate completion queues cleanup without reporting success to mac80211. Cleanup keeps the scan vdev/request, resets started/completed and finish_queued, then starts the next batch. Final cleanup cancels the overall timeout, frees ownership and reports completion. Abnormal WMI COMPLETED reasons and DEQUEUED mark a running range request aborting. Missing channels cannot be reported as success. Failed next allocation/TX drain/WMI submission/start timeout leads to aborted cleanup; requeued cleanup is cancelled on that failure path. PREEMPTED/RESTARTED events retain existing handling; eventual completion/timeout remains necessary.

**TX and recovery.** Associated batches refuse an already-stopped queue, set scan pause ownership, stop queues, synchronize networking and wait up to ATH12K_FLUSH_TIMEOUT (5*HZ) for the radio data-TX counter to empty. Completion waits min_rest_time before waking queues; another rest separates associated batches. This does not prove all management/firmware traffic is quiescent. Recovery clears scan pause ownership under the wiphy lock and bypasses the old already-stopped early exit when that stopped state belonged to scanning, then performs normal recovery drain/completion. Cleanup consequently does not wake recovery-owned queues. The earlier computed-priority assignment and wiphy deadlock avoidance remain intact.

**Timer budget.** WMI defaults are20,000ms max_scan_time and50ms min_rest_time. Associated requests add two rests per channel; host scheduling also adds the existing200ms margin. The timer is scheduled once after initial start and retained across intermediate batches, not renewed per channel. It is wiphy work, not a hard wall-clock guarantee: initial work, TX drains, command waits, sleeps and mutex scheduling can add latency. Per-batch firmware max_scan_time remains unchanged.

## Semantic correction: cancellation/timeout between batches

Source0043 was ported over0036, which added `if (ar->scan.finish_queued) break` in ath12k_scan_abort. For a single scan, an already queued completion can legitimately win. In a multi-batch scan, that flag only proves the **current batch** completed.

Concrete reachable sequence from the reviewed sources:

1. A non-final batch's WMI completion leaves state RUNNING, sets finish_queued and queues vdev_clean_wk.
2. Before cleanup acquires the wiphy mutex, cancel_hw_scan acquires it and calls scan_abort. Alternatively, the overall timeout work was queued before completion and runs first. cfg80211 appends work to its list; a firmware event can arrive while the wiphy mutex is held elsewhere.
3. Unmodified scan_abort returns without changing state because finish_queued is true. Cancellation also cancels the overall timer; a timeout callback has already consumed its one scheduled execution.
4. Cleanup sees RUNNING with remaining channels, resets finish_queued and starts another batch. Cancellation was ignored and no overall timer need remain.

**Resolution:** when RUNNING + finish_queued has an owned range request with remaining channels, set ABORTING under the existing data_lock and let the already queued cleanup finish it. Do not send a stop command for an already completed batch. Preserve the original completion-wins behavior for a final range batch or a non-range scan. This is the only executable C difference from assigned upstream after both patches are applied to the same pre0043 source; patch metadata explains it and later hunk positions are regenerated.

Manual control-flow checks against the reconstructed source (not executable kernel tests):

| Case at abort | Result |
| --- | --- |
| RUNNING, finish queued, range channels remain | ABORTING; queued cleanup cannot start another batch, cancels timer, frees request and reports aborted. |
| RUNNING, finish queued, final range batch | Existing completed result wins; final cleanup frees ownership normally. |
| RUNNING, finish queued, no range request / ROC | Existing completion-wins behavior unchanged. |
| RUNNING, no finish queued | Existing ABORTING + WMI stop path unchanged; stop failure queues cleanup. |
| IDLE / STARTING / ABORTING | Existing switch behavior unchanged. Wiphy serialization prevents timeout work from running inside the synchronous next-batch starter. |
| Non-final completion with no cancel/timeout | Normal next-batch path remains available; its finish_queued reset and overall timer preservation are unchanged. |
