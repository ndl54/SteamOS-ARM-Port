## Findings and resolutions

### Battery readings, supply scope and thresholds

Replaced the shell arithmetic/first-battery selection with a Python policy hook. It ignores explicit Device-scoped supplies (controllers/pens), requires exactly one present system/unknown-scope Battery, a decimal integer capacity in 0..100 and status Discharging. Missing presence/scope retains the PMIC-compatible defaults; malformed presence/scope, missing required fields, multiple internal batteries and other unknown readings skip protection with a log. Every non-battery system/unknown-scope supply must explicitly report online=0. An online or unreadable source cancels action, even if battery status still says Discharging. This deliberately favors avoiding an erroneous poweroff over guessing through partial probes.

Post reads all supplies twice, one second apart. Both capacities must be at or below 8%, the same battery must still be discharging and all external supplies must still be offline before requesting shutdown. A charging/full/unknown status, charger connection or second reading above 8 cancels it. A valid paired resume at <=8% can request poweroff regardless of whether the user or RTC woke it; a deadline is not treated as proof of a wake cause. This is an intentional policy difference from source079.

Two reads reduce a resume race; they cannot establish gauge freshness. Sysfs capacity has no freshness timestamp here, firmware may keep returning an old low or high value, supply attributes are not an atomic snapshot, and a charger may change after the final read. These remain device gates. No voltage/current-to-capacity conversion or treatment of a peripheral as a system reserve was added.

### RTC ownership, time, concurrency and scheduling

Source unconditionally cleared rtc0 in both pre and post, including while charging and when no matching state existed. Now an already populated alarm is left untouched. A relative `+seconds` write claims only an empty alarm; a competing active alarm causes the kernel write to fail rather than being forcibly replaced. The actual absolute alarm read back from RTC is recorded, avoiding assumptions that the system wall clock and RTC have the same offset. Cleanup clears only an exact matching recorded alarm and runs before battery sampling, so charging or missing battery data does not leave the hook's old alarm armed.

The runtime journal is atomic, validated, boot-paired, consumed once and protected by a nonblocking flock shared by pre/post. Duplicate or concurrent invocation cannot race its own journal. Invalid/stale state does not authorize clearing an alarm. Read/write errors are logged and do not block resume. State-publication failure after arming attempts matching-alarm cleanup.

This is best-effort ownership: sysfs has no compare-and-clear transaction with unrelated processes, another writer can change an alarm between reading and clearing, and process death between arming and saving readback can leave an unowned alarm. These cannot be eliminated with this local lock. The policy skips an existing alarm even if later than the desired battery check; consequently battery protection may be unavailable in that case. rtc0 remains the source's chosen RTC; there is no proof it is the wake RTC on every board.

The rate remains hundredths of a percentage point/hour: `(capacity - 8) * 360000 / rate` gives seconds. Default/floor 300 = 3 percentage points/hour; bound learned values to 300..10000. State measures elapsed time with CLOCK_BOOTTIME, not date/NTP adjustments. Learn only from >=1-hour paired intervals, decreased capacity, discharging endpoints and an increased kernel suspend-success counter. Keep the maximum valid learned rate for that battery, publish it atomically, and ignore invalid/legacy/mismatched state. Rate save failure does not prevent shutdown evaluation. Charging mid-interval, changed batteries sharing a name, failed/partial sleep and endpoint gauge lag can still make this an imperfect estimate; 3%/hour is not a demonstrated maximum.

The source's 15-minute minimum could leave an already critically low battery asleep far longer than necessary. The minimum is now 60 seconds, including <=8% at entry; maximum remains 24 hours. A system-sleep hook cannot reliably veto the sleep transaction. Even 60 seconds may be too long for a damaged battery, and no brownout-prevention guarantee is made.

### Wake attribution, resume and shutdown ordering

Removed the source's timestamp-only wake attribution and delayed automatic re-suspend. A manual wake at/after an alarm deadline is indistinguishable using that test; a late three-second timer could also race a subsequent user action or suspend. The existing diagnostic helper itself notes that pm_wakeup_irq may describe a previous event. No new unverified IRQ-name heuristic was substituted. When above cutoff or readings are uncertain, the device stays awake under the UPower policy. This loses automatic return-to-sleep and may consume more energy, but avoids silently putting an actively used device back to sleep.

[Systemd's sleep-service documentation](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-suspend.service.xml) specifies parallel hooks, waits for completion, and frozen user.slice while hooks run. The hook performs no user-session D-Bus call and retains `systemctl --no-block poweroff`, with a ten-second client timeout and failure logging. It releases the hook instead of synchronously waiting on a shutdown transaction that must stop the current sleep service. The normal systemd transaction is responsible for remaining post hooks, service stop/recovery and shutdown. There is no force-poweroff, reboot, direct power sysfs write or custom process killing. Exact real-unit ordering, job cancellation, hung recovery and actual physical shutdown remain unverified. Charger070's nonblocking shutdown implementation is byte-identical to the starting tree.

[Linux's RTC ABI](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-class-rtc) describes a one-shot wake event and relative/absolute wakealarm values. This supports the interface interpretation, not device wake capability or ownership exclusivity.

### UPower configuration

The source sed expressions silently miss commented, spaced or absent keys and do not force percentage-based policy. Added one idempotent configuration helper used by all five source paths. It sets UsePercentageForPolicy=true, PercentageCritical=6, PercentageAction=4 and CriticalPowerAction=PowerOff in [UPower], adds absent sections/keys and preserves unrelated configuration/comments. Preserve a valid existing PercentageLow above 6%; otherwise use 10% so thresholds descend. Malformed/duplicate active configuration fails without writing instead of silently producing conflicting effective policy. The [packaged UPower source configuration](https://sources.debian.org/src/upower/1.90.9-1/etc/UPower.conf/) documents percentage selection and descending-threshold requirements; the target image's daemon/version/config precedence has not been executed or inspected live.

The updater operates on an offline image path when invoked by the existing installers, never starts/reloads a host daemon. Python already exists in these recipes. Tests call only this pure file updater against temporary files; no install/build entrypoint was executed. Future user overrides/drop-ins and UPower service/package availability may affect effective behavior; PowerOff selection is not proof of physical poweroff at exactly 4%.
