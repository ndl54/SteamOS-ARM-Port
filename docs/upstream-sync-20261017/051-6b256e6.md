## Actual persistence, mount and lifecycle paths

`konkr-android.service` runs as the nonroot user, invoking `konkr-apk daemon`; it retains KillMode=mixed and TimeoutStopSec=30. Before starting Lepton, the daemon patches the installed runtime, prepares its shared directories, exports SteamAppId=konkr-android and STEAM_COMPAT_DATA_PATH=`~/Android/.android/data`, and exports LEPTON_NO_CLEANUP=true. It launches the same named container context on subsequent starts. Normal termination, idle stop and display-mode restart all reach that Lepton lifecycle. The source's new cleanup guard skips `prepare_baked_data_for_removal` when the existing no-cleanup flag requests preservation; false/unset retains the original cleanup behavior. The preexisting empty-app-id guard prevents per-app persistence setup from treating the entire shared compat directory as one app.

No new Android data directory, format revision, copy, chown, rename, deletion or symlink migration is introduced. Existing retained data continues under the same shared context. The change prevents the identified future cleanup; it cannot restore data already wiped by an earlier stop. APKs already moved into an old per-launch overlay are not copied back by this source. The existing run fallback can reinstall a saved `~/Android/PACKAGE/base.apk` if a package is missing, but does not recover its old user data or missing splits. There is no claim of automatic recovery of previously lost Google sessions.

The launcher streams base and split APKs through `cmd_real package install-create/install-write/install-commit`, bypassing the wrapper described by the source as moving packages onto a per-launch overlay. `asx` still executes inside the same named container. No fallback to wrapper-based pm installation was added: unavailable cmd_real is a failed install, preserving the input and prior user data rather than knowingly installing into ephemeral storage. `cmd_inbox` only removes its input on install success; failure retains it in the existing Failed directory. Explicit remove remains the user's uninstall path. Play Store installs use the running Android environment and benefit from retaining its shared data; they are not rewritten by this host installer.

`add_title` reads every pm-reported APK path, tries additional splits for the icon, and asks Android for a launcher activity if the base metadata lacks one. The unchanged apk-info parser reads each APK's own manifest/resources and returns package, label and activity; it is not a complete cross-split resource linker. Desktop entries still invoke `konkr-apk run PACKAGE`, and Steam shortcut confirmation is unchanged. No live package, Steam library or account was touched.

The cgroup change uses `--cgroups=disabled` inside the existing overlay guard, at the PID/IPC/UTS anchor, and removes service delegation. Its intended effect is keeping the shared Wayland client under konkr-android.service for Gamescope's existing cgroup classification. Gamescope/AppId consumers are unchanged. Actual target Podman cgroup placement and service termination behavior are unverified.

The installed proprietary Lepton scripts/image and actual Podman invocation are absent from the inspected workspace. The cleanup/mount/wrapper conclusions above follow the assigned source signatures and repository consumers, not inspection of a live Lepton runtime. A compatible known text signature remains necessary; the complete unseen cleanup function and mount graph cannot be certified from these fixtures.

## Findings and resolutions

1. **Existing cgroup patch migration.** Exact source051 applied to the actual050 patch state leaves both split and disabled options. Normalize only the exact known guarded blocks, remove old split/duplicate blocks, and emit one disabled block at the new anchor. Require a unique anchor. Keep the shared-anchor rlimit check and collapse duplicate exact LuaJIT blocks left by earlier patcher versions. Old/quoted overlay loops and old brand-inclusive/model-only property alternatives remain supported without nested identity patches or false alternative warnings.
2. **Fail before starting an unsafe runtime.** Required shared-launch, empty-app persistence and cleanup signatures must be uniquely recognized; missing/ambiguous required signatures or an unknown cgroup anchor fail patching. The daemon explicitly checks patch success even when invoked in a shell conditional context. Optional unknown overlay/property formats retain their existing warning behavior. This avoids continuing into the known data-destructive path merely because a text patch was skipped.
3. **Partial patch publication.** Compute edits in memory before publication. Each changed script is written to a temporary sibling of its resolved target, flushed/fsynced, assigned its previous mode/UID/GID, and atomically replaced. Existing script symlinks are retained. Failures stop Android startup; a later invocation can finish an interrupted multi-file publication idempotently. This does not move or rewrite Android user data. It is per-file atomic replacement, not a cross-file transaction or power-loss guarantee.
4. **Failed package sessions.** Require successful command status and recognizable Success output for create/write/commit, including zero-status Android Failure text. Validate a numeric session ID. Abandon an uncommitted known session on failure/handled TERM/INT/HUP; clear the session ID after commit so later title/OBB errors cannot abandon committed work. Temporary files are cleaned. Shell tests exposed EXIT cleanup losing function-local variables after nested die; installer state now lives in its existing isolated subshell so cleanup can still see it. No existing Android app/account data is cleared by these failure paths.
5. **Preserved earlier fixes.** Account-query failure still preserves app data and the props revision, exact image-version framework matching and stock fallback remain unchanged, and the framework builder rollback is untouched. Single-owner launch/idle locking and AppId cleanup on errors/signals remain unchanged. No migration revision was bumped just to force account cleanup.

## Remaining risks and evidence boundary

**No build/compile/package compilation, compiler syntax-only, build-script entrypoint/bundling, Android/VM/container/session/service start, live Steam/Play Store/account/network action, actual device/sysfs access, update/install/flash/deploy/reboot or device test.** Network use is limited to authorized Git verification/push. Mock preservation is not evidence of actual Google sign-in survival, installed package persistence, Play Protect acceptance, Android startup or Game Mode focus. Matching framework/common binary payloads and ART ABI remain absent/unverified as described in049. Final build/image/device validation is deferred.

Already-lost data cannot be restored. Retained old per-launch installs may still need reinstalling; this change does not attempt a speculative data migration. A live container launched before these patches may still use old loaded cleanup code when stopped. Abrupt SIGKILL/power loss cannot run cleanup or abandon sessions. If create produces a session but loses/falsifies its response, the host cannot safely identify it to abandon; Android-side reclamation is unverified. A committed install followed by a title/OBB failure may be reported as failure despite installed package state, as in the existing workflow. Idle-stop is coordinated with run/store, not a new installer lock.

Per-file replacements preserve normal mode/UID/GID and symlink targets; ACLs/xattrs, hardlink aliases, unusual filesystems, concurrent Steam updates/patchers, directory-fsync durability, insufficient permissions and target SELinux labels are not verified. Abrupt interruption may leave a hidden temporary sibling. Multi-file publication can be partial, but stops before the daemon launches and is tested to resume on known signatures. The code makes no concurrent-writer or power-loss transaction guarantee.

Unknown optional upstream patch formats still warn. Unknown required formats now intentionally prevent startup for investigation. Independent unexpected Podman cgroup options and other cleanup paths outside the supplied signatures remain runtime risks. No changes to .env, ignore rules or secrets.
