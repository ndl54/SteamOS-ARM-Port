## Mode, voltage and report format

`of_property_read_bool(..., "qcom,use-erm")` tests presence, so deleting the property is necessary; setting its cell to zero would still choose ERM. The LRA path reads the inherited nonzero 5880 us period, selects the sine waveforms and initializes LRA calibration. Constant/direct playback calls `haptics_enable_autores(chip, !is_erm)`. The old ERM path selects no modulation and skips LRA initialization. Thus the mode change has a real driver consumer.

1300 is millivolts, below the parser's 11000 mV rejection threshold; it is 26 steps on the HV 50 mV register scale. The driver also has an MV scale, runtime clamps, regulator headroom and an external-power override. This DT value is a requested configuration, not a measured terminal voltage or an absolute guarantee for every playback/calibration path. Inherited 5880 us, brake/effect settings and the driver's existing calibration fallback remain unchanged. No stock Android DT dump or measured motor characterization was provided; stock provenance and improved feel remain upstream claims.

There is no new HID/USB output report or packet format in this source. The common serial gamepad identifies as `AYN Odin2 Gamepad`, physical path `rsinput-gamepad/input0`, with DT bus 0x0003, VID 0x2020 and PID 0x3001. This bus field does not turn the UART MCU into a USB rumble transport. The userspace profiles match exact board models and the physical evdev path, and output virtual deck-uhid plus keyboard. They are unchanged.

RSInput advertises FF_PERIODIC and one effect slot, forwarding upload/playback through global Qualcomm functions. The haptics input device is named `qcom-hv-haptics`, advertises constant/periodic/gain and forces one effect slot. Sine periodic effects are converted to constant magnitude, clamped to 0..0x7fff; zero replay length becomes 30000 ms. Period/phase are not reproduced as arbitrary force-feedback waveforms. Effect IDs do not provide independent hardware effect ownership. Direct FF_RUMBLE-to-periodic translation and actual InputPlumber/Steam delivery were not executed or newly certified.

## Necessary repair on the newly enabled LRA path

Added `0061-input-qcom-hv-haptics-validate-lra-calibration.patch`. This follows from the assigned mode change, not a later queued correction.

The existing calibration reader has AUTO-mode divisions by unvalidated hardware status (`cal_tlra_cl_sts`, `tlra_ol`, `last_good_tlra_cl_sts`). Separately, `haptics_init_lra_period_config()` can successfully program the DT open-loop period after a failed/missing closed-loop read while leaving `cl_t_lra_us` zero. `haptics_hw_init()` then unconditionally divides by that zero, and repeats that operation after an unchecked calibration attempt. Its forced-period write error was also overwritten by subsequent initialization. These branches were skipped by the affected boards' prior ERM configuration.

Resolution:

- Reject zero divisors in both AUTO status branches before division.
- Treat a missing boot closed-loop period as frequency zero, entering the existing bounded recovery policy.
- After a retry, calculate frequency only on successful calibration with a nonzero period; otherwise retain frequency zero. Keep the existing maximum of three retries and existing fallback period.
- Propagate a failed fallback register write before recording the fallback as configured.

Manual source control-flow checks (not executed kernel tests): valid status/period follows the same arithmetic; either AUTO denominator zero returns EINVAL before division; missing boot period enters recovery without division; failed/zero retry remains out of range; successful in-range retry exits normally; three unusable results use the existing default; failed default write returns its error; ERM returns before the modified initialization block. No DT timing, voltage, waveform, retry count or board gate is invented by the repair.

## Ownership, errors, concurrency, suspend and disconnect

The 7.2 bridge copies latest playback ID/value under a spinlock and runs the hardware call in workqueue context, serializing bridge uploads/playback/gain with `global_ff_lock`. It loops when a request arrives during processing. Upload is synchronous and consumes the supplied effect; it does not retain the caller's ff_effect pointer. Queued playback returns acceptance, with later errors logged, not synchronous motor success. The pointer is published at successful probe; absent provider returns ENODEV. The 7.1 pin lacks the deferred 1005 bridge and retains direct calls under the haptics input event spinlock, a pre-existing sleep-in-atomic risk.

The new guard does not solve these pre-existing issues, which need final global review/runtime work:

- The global provider pointer uses READ_ONCE in 7.2 but has no reference acquisition/RCU lifetime protocol. Removal clears it and cancels playback work; an already captured pointer or a producer racing cancellation is not proved safe. A singleton also cannot arbitrate multiple providers or clients. Direct haptics-node access does not share the bridge's outer mutex.
- The constant upload path calls `haptics_load_constant_effect()` without assigning its returned error to rc, so some configuration failures can be reported as successful upload. Custom-format validation and partial calibration error cleanup are not certified by this repair; some deeper calibration helpers overwrite errors during restoration. The new guard specifically prevents the reviewed invalid divisions and fallback-write success claim.
- 7.2 suspend drains bridge playback and stop work, stops playback/FIFO, disables boost/supply/module; resume enables the module (with optional deep-sleep reinitialization). There is no producer gate proving submissions cannot race the drain, and set_gain work is not explicitly drained there. HAP_CFG_V1 has a separate early return. Removing haptics does not explicitly drain all gain/stop work/timers in the reviewed remove callback.
- RSInput suspend powers/reset-quiesces the MCU and resume restores supply/reinitializes it; removal closes UART/unregisters input and disables supply. These operations do not establish an explicit cross-device FF ownership/lifetime link. Driver unbind, producer disconnect, delayed work and suspend ordering require runtime validation.
- Existing 7.2 zero-amplitude patch 0042 remains applied; it erases a playing constant effect promptly and refuses replay without a loaded effect. Existing periodic/constant timing and multiple-client races remain outside this DTS/calibration correction.

No broad shared-driver lifetime rewrite was mixed into this item. These findings are recorded as concrete follow-up risks, not a claim that rumble is fully safe or functional.
