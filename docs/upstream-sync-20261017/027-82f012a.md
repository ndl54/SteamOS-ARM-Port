The later overlay cleanup of `/etc/wireplumber/wireplumber.conf.d` therefore cannot delete the staged source fragment. No camera override is activated for a fresh handheld image at staging time.

At boot, the exact `ConditionFirmware=device-tree-compatible(lenovo,elden)` unit copies the fragment to `/etc/wireplumber/wireplumber.conf.d/52-elden.conf` as root, with file mode 0644. The unit is wanted by sysinit, explicitly follows local-fs, and precedes sysinit/display-manager with default dependencies disabled. This places the copy before normal user/session startup without ordering the early unit after sysinit. The relative wants symlink resolves to the installed unit. ## Decoder and GPU source verification

Read exact external kernel files at [5134673b3b0492578d44c6b229477aa697b17f17](https://github.com/h0cheung/tb322fc-linux-kernel/tree/5134673b3b0492578d44c6b229477aa697b17f17): `sm8750.dtsi`, `sm8750-lenovo-elden.dts`, Iris Kconfig/Makefile and module loader. Raw downloads returned HTTP 429; GitHub contents API reads recovered all five files under `/tmp/worker027-source`. No external code was executed.

The [pinned ROCKNIX SM8750 base config](https://github.com/ROCKNIX/distribution/blob/20260901/projects/ROCKNIX/devices/SM8750/linux/linux.aarch64.conf) has `CONFIG_VIDEO_QCOM_IRIS=m`, `CONFIG_DEVFREQ_THERMAL=y`, `CONFIG_QCOM_TSENS=y`, and the step-wise thermal governor. The recipe selects that base and only `PORT_DIRS=kernel-elden`. Iris Kbuild produces `qcom-iris` (module name `qcom_iris`); the kernel loader implements `module_blacklist`. Elden's command-line builder retains the blacklist in its built-in forced cmdline. Thus this is a module-load exclusion, not a userspace-only modprobe alias. A future built-in Iris driver would not be excluded by this parameter and must be checked in final config.

Disabling Iris removes this hardware video decode/encode path. Software fallback depends on applications and can cost CPU/power; it is not guaranteed here. The older pinned DT comment says the signed VPU firmware is available, while this newer source reports it absent and reports failed opens leaving power on. Preserve the explicit new workaround but treat the firmware availability/power diagnosis as upstream observations, not verified device facts. No Android partition or real firmware/log was read.

The common builder appends `sm8750-lenovo-elden.dts.append` to the exact Elden DTS after base DTS setup. All sixteen referenced labels exist: eight `gpussN_alert0` trips in the SoC DTSI and eight `gpussN_passive` trips in the board DTS. Original trips are 105000 millidegrees with 5000 hysteresis; the appended changes set only temperatures to 90000. The board's eight cooling maps reference its passive trips and the GPU, so those are the effective board mappings; the inherited alert trips are lowered as well. Critical trips remain 125000, CPU trips and polling/hysteresis remain unchanged. This requests earlier GPU throttling, not a guaranteed 90 C ceiling or skin-temperature bound.

No runtime privileged thermal write, fan policy, suspend sequencing, GPU min/max profile or EVO DT change is introduced. The existing shared SM8750 `odin3d` is enabled broadly and can set GPU devfreq min/max profiles; it does not write thermal trip temperatures. That existing interaction and kernel thermal restoration after s2idle still need device validation. The camera file persists across suspend, and the module blacklist remains effective for later module-load attempts. Nothing here establishes resume/audio recovery or touchscreen/body temperature under load.
