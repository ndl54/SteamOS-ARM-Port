## Findings and resolutions

### Preserve060 and make retained settings truthful

Kept `is_transient` byte-identical to starting main: canonical keys, exact managed code roots, `.pyc` directly inside `__pycache__`, and only direct `.db`, `.files`, `.db.sig`, `.files.sig` files in the canonical pacman sync directory qualify. Broad substring matching from source066 was rejected for the same reasons established independently in060.

Added upstream's exact SETTINGS tuple and extended the existing guarded planner loop to those two paths. Both existing parents and leaf are checked by lstat: parents must be real directories and the leaf a regular file. A directory or leaf/parent symlink fails with a nonretryable type/path error. A missing setting has no user copy to preserve and stays in `write`, so missing content still requests full fallback. Supplied blobs follow the ordinary verified write path.

Source066 only removed retained settings from `write`. That would cause apply2 to record the release hash against the retained user's different bytes, seeding a false size/mtime shortcut on the next update. Retained settings now enter the060 `skip` list and are excluded by the existing inventory filter. Signed target and fingerprint are unchanged. Tests reproduce this false-hash bug with the exact source helper and verify next-plan rehash, retained bytes and rollback of the previous inventory.

Cache behavior remains: staging only edits plans; present stale pyc deletion is backed up and happens in offline apply; pacman missing-blob caches are retained. No additional cache exemptions or live deletion were introduced. The apply2 change is only a comment clarifying that its already-existing skip filter also covers settings.
