## Review findings and repairs

The source adds four identical patches. Its premise is plausible from the code: glue system suspend disables clocks independently of runtime-PM status. The synchronous USB-role notifier is invoked before `dwc3_set_mode()` queues actual core role work on a freezable workqueue. Freezing the latter does not by itself serialize the former with system PM. A runtime get returning for an already-active status is not proof that system-sleep glue clocks are enabled. The source's reported reset on RP6/Pocket FIT remains an author claim, not hardware evidence from this review.

1. **New pending state was unsynchronized.** The USB role-switch mutex serializes its own callers, not the added system-resume consumer. In the source, resume clears pm_suspended before replay, allowing a newer notifier to update hardware/current_role and then be overwritten by the older pending role. A notifier that has observed suspended=true can also publish pending state after resume has already checked it, leaving the update stranded. The suspend flag is set only after clocks are disabled, so the flag test alone does not exclude that entry window.

   Added a per-device `role_lock`, initialized before core probe registers callbacks. The normal notifier and both system-PM callbacks share it. It covers the pending/current-role update and the full core/glue suspend/resume boundary. The notifier records the latest request under the lock; suspended requests exit without a runtime get or QSCRATCH access. Successful normal requests obtain/release one runtime-PM reference while holding the lock and update current_role before releasing the PM reference.

2. **Source replay consumed state too early and used runtime PM inside system resume.** Source cleared role_pending before calling a void helper that can fail its runtime get, silently losing the deferred update. It replayed before `dwc3_pm_resume()` reconciled runtime state and restored the core. Depending on status/errors, this can invoke runtime callbacks against a partially resumed controller or fail without applying the role; it is not an unconditional deadlock claim.

   Split hardware application from runtime-PM ownership. The hardware helper contains the original same-role shortcut and VBUS override behavior, with no runtime get/put. System resume first resumes the glue, then the core, then directly applies the pending role under role_lock, clears pending, and publishes pm_suspended=false. Both resume failure exits unlock and retain pending/suspended state. Normal notifier PM-get failure also keeps the latest pending request. No worker, timer, global pointer or new teardown lifetime was added.

   Reviewed core runtime suspend/resume, gadget run/stop notifier and OTG paths: runtime callbacks do not take this new mutex, so the notifier's synchronous runtime get/put does not recursively acquire it. System callbacks do not acquire the USB role-switch mutex. Every new locked error path reaches one unlock; probe initializes the lock before publication. This is source lock-order reasoning, not lockdep or scheduler testing. Existing core/glue error recovery, interconnect warnings and IRQ behavior remain as inherited.

3. **TB321FU inherited patch overlap was real.** Replaying the original assigned patch followed by existing tablet 0012 fails two of seven DWC3 hunks at fuzz zero. The tablet changes the same notifier for host PHY reinitialization and SS power-up sequencing. Rebased only that tablet patch's DWC3 diff onto the repaired common helper. Both quirk predicates/calls now reside in the clocked helper and therefore run in both normal and deferred role application. All original added tablet C lines, complete PHY/SS helper bodies, properties, probe hooks and debug messages are preserved. All other driver sections, including mixed line endings, remain byte-for-byte identical.

   No tablet skip or later correction was imported, and no soc.env was changed. **Follow-up integration constraint:** tablet 0012 now expects this inherited DWC3 patch. If a later queue source changes that selection, its worker must independently rebase/review the tablet hunk context; simply dropping 0057 would leave the rebased 0012 incompatible. That later source is outside 084 and was not read or integrated.

The four shared patch copies remain byte-identical. Patch descriptions now distinguish reported hardware symptoms from verified source behavior. No unrelated VBUS, charger policy, DT wake-source or PM algorithm redesign was attempted.

Tablet PHY helpers still warn/continue on individual failures and may not fully restore a failed PHY operation; their existing error semantics are preserved.

A failed runtime get retains pending state but does not schedule an autonomous retry; a later notifier or successful system resume is needed. Direct-complete/runtime-suspended paths that skip system callbacks are still controlled by the PM core and were not redesigned. Core-resume failure keeps the new gate closed; this avoids replay against failed state but does not repair the inherited hardware failure. The existing wake IRQ reads pm_suspended outside role_lock, and alternate gadget/OTG/firmware paths are not proven safe by this notifier-only audit. No universal USB/charger recovery guarantee is made.
