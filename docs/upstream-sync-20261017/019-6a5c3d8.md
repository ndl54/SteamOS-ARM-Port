`build-update-v2.py` imports the updater's managed-tree inventory code. It inventories regular files, directories, links and applicable overlay whiteouts, excludes preserved identity/credentials and the self-written installed record, and explicitly adds the selected boot/KERNEL. Root keys resolve under the rootfs, while home keys resolve under its home directory. File contents are indexed and deduplicated by SHA256. Both a previous package's inventory and a release's installed.json are converted into per-path hashes; an ordinary blob is required unless every supplied base has the same hash at that same path. An identical hash at another path does not satisfy that condition.

The source adds `stale_pyc` as an additional reason to include a regular file's hash. It considers .pyc files directly under __pycache__, maps the cache name (including optimization tags) back to the corresponding .py source, reads header flags/mtime/size, and compares timestamp-format metadata with the source's integer mtime and byte count, masked to 32 bits. It detects both older and newer mismatches, not just a numerically older timestamp. Flags 1/3 (hash-based caches), missing sources, inaccessible files and non-cache paths are outside this predicate. Inspected the host CPython 3.9 `_validate_timestamp_pyc` implementation: its timestamp and source-size comparisons use the same 32-bit masks. This is local implementation evidence, not verification of the Python version shipped on a device.

Full-package selection still includes all regular blobs. Delta manifests, inventory entries, signatures, content-addressed layout and archive creation are unchanged. An extra blob is useful even if unchanged from the release inventory: Python may have rewritten the device's copy since installation. Selection remains deduplicated when multiple stale cache paths share bytes.

`install-vendor-apps.sh` copies the UFS installer tree to /usr/share/easy-ufs-install and installs the updater to /usr/share/konkr-update. Shared and SM8750 overlay scripts record inventory at the end. The update agent downloads/copies and checks the package before launching the already-installed updater's `stage` command. In format 2, staging verifies the signature, architecture, model and managed paths; `make_plan` compares installed size/mtime/hash with target entries. A changed cache becomes a write. The historical consumer then rejects any write whose target hash is absent from manifest.blobs, before the newly shipped updater could replace it. This explains why only updating consumer code cannot repair compatibility for that older installed consumer.

The current consumer first calls `drop_stale_pycache`: a drifted cache without a supplied blob is removed from writes and scheduled for deletion, whereas a supplied stale blob stays a write. Staging extracts needed blobs and verifies hashes, backs up affected paths, then recovery's `apply2` installs the bytes, checks installed hashes and records inventory. This source alters only what the producer supplies; it does not invoke staging/recovery or change their rollback, preservation, signature or board checks.

## Limits and remaining risks

No package, kernel, Gamescope, InputPlumber, rootfs or image build; no signing, archive generation, VM/container startup, mounting, installation, update staging/recovery, flash or deployment. Build validation remains deferred until all 109 integrations complete. **Not hardware tested.**

The source author's statement that release 1.3.0 shipped two stale UFS installer caches was not independently verified against release artifacts or a device. The fixture simulates the resulting byte/mtime drift; it never imports or regenerates bytecode. Actual signed-package compatibility, recovery, final Linux/Python versions and device behavior remain later checks.

This is a targeted timestamp-cache compatibility fix, not a general repair of arbitrary device modifications, hash-based invalidation, malformed caches, missing sources or unknown Python cache layouts. The helper does not validate magic/header length and reads each examined cache fully before slicing 16 bytes; these remain existing characteristics of the accepted source. Missing/unreadable candidates are not forced by this predicate. Reinstalling stale bytes does not make them valid: a later Python import may rewrite them again. A coherent later package must continue supplying required bytes, or an updated consumer can use its existing deletion fallback.
