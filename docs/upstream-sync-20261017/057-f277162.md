## Audio: Gen 3 pro-audio with explicit tablet routing

Source replaces the tablet's unsuccessful HiFi profile preference with pro-audio plus a per-user route service. The fork already bypassed this tablet in the generic Odin audio policy. Kept the exact NUL-separated `lenovo,tb321fu` early return (updated its comment), all EVO/FIT/S2/SM8250 UCM handling and the separate setup-helper bypass. Resolved the priority-list conflict to pro-audio only, while retaining the fork's exact card/node matches and its `/usr/share/steamos-arm/tb321fu` payload copied into `/etc` by the early setup unit. Thus the tablet override still loads after the broad FIT 53/54 rules; simply naming a `/usr/share/wireplumber` file 90 would not achieve that precedence.

The dedicated service and direct helper both gate exact TB321FU. Replaced source's hard-coded ALSA ID/platform name with a unique matching Pulse card selected by `alsa.card_name` or `api.alsa.card.name` and its numeric `alsa.card`. Both `Lenovo-Y700-TB321FU` and `Lenovo-QRD-2.0` are accepted; missing/ambiguous cards fail, and unrelated USB cards are excluded. Sink/source names derive from that card, selecting PCM0 output and PCM2 capture. The local HiFi verb still routes speakers through Secondary TDM from MultiMedia1/PCM0, headphones through RX codec DMA from PCM0 and microphones through MultiMedia3/PCM2. This preserves the prior speaker-first behavior in the new routing mechanism: no headphone jack means Speaker; no mic jack means Mic1, including ordinary headphones without a headset mic.

Startup now selects `off`, sets the UCM route, then selects `pro-audio` so old UCM teardown precedes our mixer setup and PCMs open after their routes exist. Mixer/profile/default/initial-volume failures propagate; a failed route is not remembered as successfully applied. The initial-volume marker is written only after required setup succeeds; subsequent starts preserve user volume. External commands have eight-second timeouts. Profile disappearance retries initialization; jack changes update routes, and failure exits for the unit's restart policy. This is not a full generation/event subscription to WirePlumber: a restart with indistinguishable still-present nodes can still need runtime investigation.

A new alsaucm process does not remember the preceding process's enabled devices. Added four speaker-amp disable controls to the local HiFi verb's initial sequence, alongside its existing backend clears, before enabling the selected output. Reviewed alsa-lib's `set_device`, `do_reset` and `set_defaults`: `reset` executes defaults, not every device's DisableSequence, so the implementation does not rely on that false assumption. Existing CardId normalization, all direct-include checks and content-addressed original UCM archive are retained. Only the stale “same commit as kernel” comment in release.env changed; its URL/hash are unchanged. The newer package's audio tree is not silently substituted for the separately pinned profile.

Source's +6 dB stereo limiter applies to the Gen 3 pro-output-0, including headphones; added the QRD alias and exact PCM suffix boundary. Gen 4 keeps +8 dB on its named Speaker node. This is software gain/limiting, not measured loudness, speaker protection or proof of acoustic safety/absence of clipping. User/higher-priority WirePlumber configuration may override it.

## First firmware boot, charge and Turbo

The firmware conflict retains the fork's changed-file marker, exact Elden gate, PCI/Wi-Fi retry logic and nonblocking Bluetooth restart. Source's `before` counter no longer existed in this fork; using it under `set -u` would fail. A fresh empty firmware destination now gets a persistent pending marker before extraction. Failed/partial extraction does not consume it. Once both nonempty ADSP headers exist, the helper persists a completion marker and requests one nonblocking reboot; a rejected request removes completion and remains retryable even if the next extraction changes no files. A successful request returns before unnecessary device recovery. Existing populated installations do not get an unsolicited reboot solely because firmware is updated.
