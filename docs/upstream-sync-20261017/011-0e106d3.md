## Repairs during integration

1. **Shared audio policy undid tablet UCM.** The enabled `sm8550-audio-pipewire` otherwise sent the tablet down its generic Odin path, selecting pro-audio and applying unrelated MI2S mixers. Return immediately only for exact NUL-separated `lenovo,tb321fu`; WirePlumber owns the tablet's UCM. The installed SM8650 setup helper now also returns for that board after permissions normalization, retaining its EXIT readiness marker. This avoids waiting for a handheld card name and avoids another card selecting the wrong mixer path. Removing these two small guards reproduces both starting helper files byte-for-byte. EVO's own UCM-only policy and all other handheld behavior remain intact.

2. **Both card aliases used one hard-coded ID.** The external HiFi file hard-codes `LenovoY700TB321` in seven PCM, mixer and control references, despite providing a QRD alias. Rewrite these references only in the installed TB321FU HiFi file to ALSA's `${CardId}`, already used by this fork's EVO profile. Check every direct absolute File/Include path in the installed tablet configs (15 unique paths), including capture and disable sequences omitted by the source's six-file check. This does not validate all transitive includes or ALSA control availability; real rootfs validation remains required.

3. **Unverified fixed cache name could reuse unrelated profile bytes.** Pin the downloaded archive SHA256 as `9feab840a48ea6451011c8db8c251cd563b3b5cf3c455dfefbab54c8dd96c4e8`, use it in the cache filename, and pass it to the existing checksum-verifying fetch helper. A cached mismatch now fails before profile extraction. The URL remains the source's exact `1cfa907237d190c03db9392cd858de2208eb7892` commit. Correct the stale GUF-package comment: that package now supplies Bluetooth/touch firmware, not UCM. The optional kernel wrapper itself is unchanged.

4. **USB recovery trusted remoteproc0 and rebound after timeout.** The pinned tablet DT enables both ADSP and CDSP with distinct firmware names. Discover the ADSP by its exact firmware path across remoteproc indices, require `running`, and fail without sysfs writes after the bounded wait. The [PAS driver](https://github.com/torvalds/linux/blob/v6.19/drivers/remoteproc/qcom_q6v5_pas.c) passes DT `firmware-name` into remoteproc, and [remoteproc sysfs](https://github.com/torvalds/linux/blob/v6.19/drivers/remoteproc/remoteproc_sysfs.c) exposes it; these are source API references, not a device probe. Add the same exact board guard inside the helper for direct invocation. Keep an existing Type-C port untouched, check driver availability, unbind only a bound device, propagate write failures, and set a 90-second service timeout. Preserve the source's eight-second grace period and driver/device names, consistent with the [UCSI GLINK driver](https://github.com/torvalds/linux/blob/v6.19/drivers/usb/typec/ucsi/ucsi_glink.c). A successful bind write still does not establish eventual port/charging/audio recovery.
