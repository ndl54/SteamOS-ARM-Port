## Actual consumers and ID semantics

The source adds a root system oneshot plus multi-user.target enablement symlink. It intends to prepare steamos's subuid/subgid files before login, requesting 131072 subordinate IDs rather than the stated default 65536. `scripts/apply-overlays.sh` copies the common SM8650 overlay into the shared image path and restores executable permission to every shebang helper under /usr/lib/konkr, so the new helper/unit/drop-in are staged for the EVO/common image without modifying the staging script.

The actual `konkr-android.service` is a **user** unit with ConditionUser=!root, not User=steamos. `konkr-apk` uses HOME, the current UID's runtime directory and unprivileged `podman exec` against `lepton-steamlaunch-konkr-android`. The daemon launches the installed Lepton as that user. Thus the source helper provisions only the stock steamos account; it cannot fix a different login user's mapping. The repaired helper resolves steamos through pwd, supports its real numeric UID (not an assumed 1000), and recognizes that UID as owner in BOTH files: the owner column of subgid is a user name/UID, not the user's primary GID. Missing account/query errors are explicit failures. No user is created or selected from SUDO_USER, an arbitrary UID1000 account or the currently logged-in session. The framework builder's existing hardcoded steamos/UID1000 assumption is untouched and remains a separate limitation from049.

Subordinate ranges allocate **host** IDs. Their count is not the number of processes and their start is not an Android UID. In the common single-extent rootless mapping, container root maps to the login UID and container IDs 1..N map to start..start+N-1. Under that conditional model, 65536 does not include Android's source-stated isolated IDs 90000..99999, whereas 131072 does. For example, start100000 would place container90000 at host189999. This is explanatory arithmetic, NOT an observed Lepton uid_map/gid_map. The repository does not contain the complete installed proprietary Lepton launcher/image or its actual Podman namespace options. Extra keep-id/auto/uidmap/gidmap options or later Android users can invalidate that model; this count does not promise arbitrary Android multi-user ID coverage.

The repaired arithmetic uses Python integers and exclusive ends, permits last host ID4294967294 and rejects reserved ID4294967295, zero/negative counts and overflow. It checks all parsed allocations against the target's expanded range, including numeric aliases, and rejects overlapping host UID/GID account IDs. GID collision checks include primary groups from passwd as well as group enumeration. Sufficient single custom extents are byte-preserved; existing starts and record ordering never change. Multiple extents are deliberately not combined or reordered, even if their total looks sufficient: actual consumer mapping is unknown.

Existing `--ulimit stack=-1:-1` is a distinct inherited stack/mmap policy for zygote descendants. Extending IDs changes neither stack, nproc, nofile nor other inherited limits. Existing `--cgroups=disabled`, no Delegate=yes, shared HOME/Android/.android data, LEPTON_NO_CLEANUP=true, required persistence signatures, cmd_real package sessions and account-query-failure preservation all remain byte-identical. No data initialization, ownership migration, app reset or props revision bump was added.

## Findings and resolutions

1. **Source relocation breaks retained ownership.** For steamos:100000:65536 and other:165536:65536, the exact upstream helper moves steamos to231072:131072, changing all previously mapped subordinate IDs. Reproduced this on ordinary temporary files, using only a GNU-sed-compatible deletion stub on macOS. Repaired behavior refuses the collision and preserves both files; an explicit mapping/storage-aware migration is required. It does not guess that retained /data or Podman storage is disposable.
2. **Source deletes custom extents and ignores aliases.** Its first steamos line determines capacity, then sed removes all steamos lines. Numeric UID entries are treated as another user. It also skips collision checks for an already-large count, has no ID bound checks and treats malformed/missing content and account state as permission to initialize. The replacement recognizes name/numeric owners, validates records and rejects missing/multiple/invalid/conflicting allocations. Missing files or allocations do not cause speculative fresh allocation. This is an intentional conservative deviation: such installations need administrator inspection and may still lack enough IDs.
3. **Do not report failed writes as success.** Upstream has no errexit and ends with exit0 after touch/sed/append failures; it updates one file before even inspecting the other. The Python helper propagates errors, preflights both files and stages both replacements before publication. It requires regular single-link files, preserves mode/ownership and copies available xattrs before fsync/rename. Symlinks/hardlinks are rejected. Each rename is atomic; a second-rename failure leaves a safe additive first expansion and returns failure, with retry completing the second. No two-file transaction or power-loss guarantee is claimed.
4. **Serialize cooperating account edits.** A nonblocking POSIX lock on /etc/.pwd.lock serializes this helper and normal glibc shadow operations using lckpwdf. [Shadow's commonio source](https://github.com/shadow-maint/shadow/blob/master/lib/commonio.c) makes that global lock conditional on build/configuration and non-prefix operation; arbitrary editors, prefix operations and other providers are not universally serialized. Recheck file bytes before replacement and document quiet-boot administration. The helper accepts absent/default or explicit files subid provider and refuses configured non-file providers. NSS enumeration cannot prove absence of non-enumerable remote users.
5. **Linger ordering and inherited namespaces.** The original Before=systemd-user-sessions.service alone does not order a lingering user manager. Added a user@.service drop-in with Wants/After for the helper, retaining the source's normal boot ordering. Wants makes failure visible without preventing every user login; it is not a guarantee Android cannot start with insufficient IDs. The helper performs no Podman action and does not update existing namespaces. [Podman's migrate documentation](https://docs.podman.io/en/latest/markdown/podman-system-migrate.1.html) explains that the rootless pause process retains mappings until it and associated containers are stopped. An ordinary Android restart may be insufficient; later explicitly scheduled migration or a clean reboot needs target verification. No automatic container stop/reset/recreation or data chown is introduced.
6. **Operational documentation.** Expanded docs/android-apps.md with the stock-account scope, conservative failure behavior, mapping-vs-host distinction, boot/restart boundaries and partial-write recovery. No claim that this integration by itself fixes actual Chrome/zygote startup.
