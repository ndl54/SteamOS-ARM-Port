## Independent review

The source changes only two overlay recipes and a new Bash launcher. The
launcher reads the first `xrandr --current` screen width, reads `Xft.dpi`,
computes `floor(96 * width / 1280)`, globally merges that DPI when lower,
then execs Steam. There is no KWin script, window-class/title match, keyboard
surface detection, or per-window sizing in this commit.

1. **Shared state / other windows:** `xrdb -merge` writes X server resource
   properties shared by clients. It cannot target Steam's keyboard and may
   affect other Steam UI or unrelated X clients that read those resources.
   An explicit user DPI is overwritten for the session without an ownership
   marker or restoration. This conflicts with the fork's preservation of user
   display choices. X.Org documents this server-wide resource mechanism in
   [xrdb(1)](https://www.x.org/releases/current/doc/man/man1/xrdb.1.xhtml).
2. **Geometry / units:** the screen width is a desktop framebuffer dimension,
   not the selected keyboard monitor's usable workarea. A side-by-side 1240
   and 1920 layout can report 3160, yielding a fit DPI of 237 and no correction
   at DPI 120, although the keyboard still may not fit the narrow output.
   The wrapper has no output selection, reserved-panel/workarea subtraction,
   rotation or Xwayland-to-KWin coordinate conversion. KWin logical geometry
   and physical panel pixels cannot be assumed interchangeable. See the
   framebuffer/output distinction in
   [xrandr(1)](https://www.x.org/releases/current/doc/man/man1/xrandr.1.xhtml).
   The source's 1280-pixel keyboard assumption is not verified against a live
   Steam client in this review.
3. **Scaling / parsing:** integer-only parsing discards fractional DPI;
   malformed or tiny positive widths can produce implausible DPI (including
   zero). Even valid lowering changes a global preference, rather than a
   keyboard-only setting. Replacing it with a Steam-wide scaling flag would
   still affect other Steam windows and is not an equivalent safe repair.
4. **Lifecycle:** sampling only at autostart misses later monitor changes,
   rotation, scale changes, keyboard placement and reserved-area changes.
   Existing Steam processes need not reread DPI when invoked again. There is
   no display-ready retry or handling of a later KWin resource update.
   Temporarily changing and restoring xrdb would still race other clients and
   cannot prove when Steam consumes/caches the resource; that alternative was
   not implemented.
5. **Autostart:** the upstream sed replacement matches only an unquoted
   `/usr/bin/steam` followed by a space and is not restricted to the main
   Desktop Entry group. A different valid Exec format fails the subsequent
   grep, while matching desktop actions can also be rewritten. No installed
   rootfs/autostart contents were assumed or executed. Removing this rewrite
   preserves all existing launcher formats, flags and user overrides.
6. **Fork context:** inspected `sm8550-startplasma`,
   `sm8550-prepare-plasma`, `desktop-outputs`, `desktop-fit`, and the relevant
   installer defaults. Startup uses Plasma Wayland; `desktop-outputs` already
   models rotation, scale, dual panels and preserves user-owned layouts,
   including EVO's model. No change is made to those paths, KDE config,
   Game Mode's existing DPI policy, controllers, sleep, audio or kernels.

## Resolution and scope

`desktop-steam` now only uses `exec /usr/bin/steam "$@"`. It performs no X,
KWin, sysfs or config operation and creates no watcher or background process.
Arguments and exit status pass through; normal exec process/signal semantics
are retained. Both recipes install the compatibility entry point with mode
0755 but leave Steam autostart untouched. On a fresh image the new helper is
not automatically selected; an existing launcher referencing it remains valid.
No persistent user configuration is introduced. No later source was included.

For each overlay recipe, removing the three-line installation addition gives
byte-for-byte pre-093 content. Every other previously tracked product path is
unchanged, preserving EVO protections and all 083–092 integrations. Prior
075 critical GPU trips, 076 haptics lifetime/concurrency and 078 Elite gain
findings remain in the final-global review scope.

## Remaining risks and evidence boundary

The clipping fix is withheld, so narrow-panel Steam keyboards may still exceed
their output/workarea. A future implementation needs verified keyboard identity
and a supported keyboard-specific sizing mechanism, tested with the actual
Steam/KWin versions, fractional scaling, rotation, multi-monitor placement,
reserved panels, reopening and hotplug. No runtime-safe mechanism is established
by this source alone. The separate existing Plasma touch keyboard is unchanged.

No build, source-preparation entrypoint, compilation, package installation,
rootfs/image operation, flashing, deployment, real desktop/window/sysfs change
or device test was performed. No checkpoint was edited. Source/mock checks do
not establish Steam rendering, KWin behavior or hardware success.
