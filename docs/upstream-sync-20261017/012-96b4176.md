## Review and execution paths

Read the protocol and reports 009–011, reviewed the complete two-file source diff, the complete fork collector, initramfs argument parsing and service generation, both overlay installer paths, file-trigger service, Elden recipe/config and firmware extractor/wrapper/unit. Also inspected the existing source/fixture isolation checks before running them.

`kernel-common/build.sh` packages bootdebug into the initramfs. When debugging is enabled, `/init` copies it into the real root and generates `steamos-arm-bootdebug.service` with `Type=simple` and `After=local-fs.target`. It runs under the real root's `/bin/sh` and utilities after switch_root, not as an early BusyBox display program. Both overlay installers also install the collector; the SM8750 installer copies the SM8550 file-trigger service. That service suppresses itself when the generated unit exists, preserving normal duplicate-start prevention.

The new explicit `steamos.screenlog=1` mode starts a background report before the collector's USB polling. After 75 seconds **from collector service start**, it requests stopping `display-manager.service`, waits three seconds, switches to VT1 and refreshes the report every 30 seconds. Service ordering and stop duration can add delay; this is not an uptime-75 guarantee. Firmware extraction can still be running at the first refresh. It deliberately ends the graphical session/Game Mode and does not restart it automatically.

The report reads the current boot's firmware-service journal, selected GPU kernel messages, filtered UID 1000 Game Mode messages, failed units and DRM connector status/modes. It writes only to `/dev/tty1`; journal queries explicitly disable paging. The source's 14/16/30-line tails and 118-character truncation are retained. This is a selected diagnostic view, not the complete collected logs. It does not display the early initramfs bootlog or previous-boot journal.

The ordinary file collector retains `/boot/debug-logs`, or the owned `/run/steamos-arm-usblog/debug-logs` USB destination when /boot is absent and a usable USB device is found. Its snapshot/runtime/performance schedule and DONE markers are unchanged. The report neither uses that destination nor prevents owned-USB cleanup when capture ends. Early initramfs logging and the independent EVO sleep-stages writer retain their existing destinations.

Elden's recipe already sets `steamos.debug=1`, `console=tty0` and `fbcon=font:TER16x32`, but does not set `steamos.screenlog=1`. This integration does not enable screen mode by default or alter a kernel recipe/cmdline. A later explicitly selected debug image must actually deliver the screenlog parameter; a forced built-in cmdline may ignore bootloader additions. No image was built here.

The firmware change promotes only the `/dev/kmsg` summary from priority 4 to 3, making it eligible at console loglevel 4. Standard journal logging, extraction, alias preservation, slot selection, coherent MDT bundles, changed-file marker, mount policy and boot retry logic from 010 are otherwise byte-identical. Console visibility still depends on a working kernel console and its loglevel; writing kmsg is not panel validation. See the [kernel printk documentation](https://docs.kernel.org/admin-guide/sysctl/kernel.html#printk).

## Conflict resolution and integration repairs

1. **Preserve EVO collector and USB fixes.** The textual conflict was at log-directory creation and the adjacent EVO release/pstore/runtime-evidence block: upstream adds a blank line where this fork has its extra collection. Retained the destination-aware error and all fork content. The entire pre-existing collector, from its first `mountpoint -q /boot` through its final `sync`, is byte-identical inside the new `collect_logs` function. The exact `ayaneo,pocketevo` gate and setup prefix also remain byte-identical.

2. **Activate the advertised mode through both service paths.** The source checks screenlog only inside bootdebug; neither initramfs nor the fallback unit starts it for screenlog alone. Add the exact token to initramfs's debug case and the fallback service condition. Existing debug/debug.txt files and `steamos.debug=1` still work, and generated-unit suppression is retained. Screenlog now also activates existing early-debug capture through the common initramfs.

3. **Require an exact opt-in before stopping Game Mode.** The source uses `grep -qw 'steamos.screenlog=1'`; its unescaped dot and word boundaries accept `steamosXscreenlog=1`, `foo-steamos.screenlog=1` and `steamos.screenlog=1-extra`. Use escaped-dot, whitespace-delimited tokens in bootdebug and the fallback condition. The latter likewise makes the existing debug parameter exact, consistent with initramfs parsing.

4. **Keep the screen report alive independently of file capture.** In the source, the main process exits if log-directory creation fails, or when capture finishes. A background report alone does not keep these `Type=simple` services active: the default main-process exit policy stops the service, and default control-group cleanup kills remaining processes. See systemd's [service lifecycle](https://raw.githubusercontent.com/systemd/systemd/v257/man/systemd.service.xml) and [kill policy](https://raw.githubusercontent.com/systemd/systemd/v257/man/systemd.kill.xml). In screen mode only, run the unchanged collector in a subshell, then wait for the report. Collector exit/USB traps execute in that subshell before the parent waits. Without screenlog, call the collector directly and retain its existing exit/trap behavior. The service intentionally remains active while the report runs. No KillMode override or detached process escapes service management.

5. **Check the console before ending the session.** Require a character-device tty1 and successfully open it before the delay/stop operation; otherwise the report worker exits while file collection continues. Set `TERM=linux` explicitly for setterm because a system service may have no useful TERM. Keep diagnostics noninteractive with `--no-pager`, parse whitespace-padded failed-unit names with awk, and quote panel sysfs paths. A usable tty node does not prove framebuffer handover or a visible panel.

Product edits are limited to the two source files and their directly coupled initramfs/fallback activation paths. EVO kernel/patches, UFS-bound sleep behavior, Wi-Fi restore/scan, audio/UCM, LEDs, Gamescope and all tablet installers remain untouched. The 009 USB candidate retry, USB ancestry check, occupied-target guard and owned-mount cleanup remain intact, without stacking or unmounting another owner's mount.

No display-manager restart or terminal-state restoration is added; this remains a deliberate debug boot mode. Normal boots without the exact screenlog token never run the screen worker.
