## Audio findings and resolution

The source replaces `51-lenovo-tb321fu-alsa.conf` with a `90-` fragment, adds both `alsa.card_name` and `api.alsa.card.name` exact matches for `Lenovo-Y700-TB321FU` and `Lenovo-QRD-2.0`, selects the microphone-bearing HiFi profile, and sets 1024-frame periods/quantum, four periods, zero headroom and timer scheduling. Its profile preference list is internal Mic1, headset microphone, plain HiFi, then pro-audio.

**The source's directory choice defeats its intended precedence.** WirePlumber loads fragments by directory priority, with alphabetical ordering only within each directory. `/etc` follows `/usr/share`, so `/usr/share/.../90-lenovo-*` still loses to `/etc/.../52-sm8550-alsa.conf`, `53-konkr-audio.conf` and `54-konkr-quantum.conf`. The local rule model reproduces the wrong headphone/speaker-only device profile, 960-frame playback periods/quantum, 2048 headroom and interrupt scheduling. This follows the [documented load order](https://pipewire.pages.freedesktop.org/wireplumber/daemon/locations.html) and [WirePlumber 0.5.12 directory iterator](https://github.com/PipeWire/wireplumber/blob/0.5.12/lib/wp/base-dirs.c); it is not merely filename inference.

Repair: store the fragment as an inactive template under `/usr/share/steamos-arm/tb321fu/`, and add a second ExecStart to the existing exact-board setup oneshot. At boot it copies the template into `/etc/wireplumber/wireplumber.conf.d/90-lenovo-tb321fu-alsa.conf`, after local filesystems and before sysinit/display-manager. Both obsolete `/usr/share/wireplumber` 51/90 files are removed during staging. The live `/etc` copy also reaches the persistent upper layer rather than relying on an image's lower `/etc` file. A fresh combined rootfs does not activate the tablet fragment for another board; its properties additionally match only the two Lenovo card names. Existing FIT/SM8550 rules and the APS2-only speaker filter are unchanged.

[WirePlumber 0.5.12 ALSA monitor source](https://github.com/PipeWire/wireplumber/blob/0.5.12/src/scripts/monitors/alsa.lua) copies `api.alsa.card.*` properties into node properties before applying rules. Thus the additional match reaches playback and capture nodes as well as the card. [find-preferred-profile.lua](https://github.com/PipeWire/wireplumber/blob/0.5.12/src/scripts/device/find-preferred-profile.lua) consumes the priority list; stored user profile selection precedes it. These are inspected upstream reference sources, not evidence of the precise WirePlumber binary in a future image.

The pinned UCM defines Speaker on PCM1 (AW882xx, Secondary TDM), Headphones on PCM0 (WCD939x), and mutually exclusive Mic1/Headset on PCM2 (TX_CODEC_DMA_TX_3). All seven `${CardId}` references, both card aliases and the direct-include checks from 011 remain. ## USB findings and resolution

The source introduces two generated helpers, two enabled services and a udev rules file. The GPIO helper locates TLMM by `f100000.pinctrl`, leaves an owned line alone, and otherwise holds line 58 high with libgpiod 2 `gpioset`. The role helper waits two seconds and requests host on `a600000.usb-role-switch` while `port1-partner` exists. Services retain `ConditionFirmware=device-tree-compatible(lenovo,tb321fu)`.

The local TB321FU common DTS declares `c2-select-gpios = <&tlmm 58 GPIO_ACTIVE_HIGH>`, two dual-role Type-C connectors and OTG/role-switch support. Its existing kernel patch `0012-usb-typec-the-tb321fu-type-c-ports.patch` acquires c2-select at probe, defaults it high, and changes it for single-connector attachment. The normal tablet recipe layers these patches over SM8650 in its separate kernel; EVO has its own recipe. **This source and integration do not change any kernel source, DT, patch or config.** The optional 7.2.6 path is still separate; actual GPIO ownership, not a version-string assumption, selects the userspace fallback.

Repairs made:

1. **GPIO/ADSP ordering and failure handling:** the data-port service now requires and starts after the existing UCSI recovery service, allowing UCSI to acquire its GPIO before a userspace request. The unchanged recovery helper discovers the ADSP by `qcom/sm8650/lenovo/tb321fu/adsp.mdt`, waits for running, and refuses a rebind on timeout. Both new helpers also guard direct invocation by the exact compatible. GPIO discovery/info errors now fail without trying to set a line; any consumer is left untouched without claiming that it must be the kernel. `gpioset` retains ownership for its process lifetime, as documented by [libgpiod](https://libgpiod.readthedocs.io/en/master/gpio_tools.html). Required libgpiod 2 utilities in the final rootfs remain a packaging check, not something installed here.

2. **Repeated role events:** `SYSTEMD_WANTS` activates units when a device first becomes active, not on every subsequent change/removal. This is explicit in [systemd.device](https://www.freedesktop.org/software/systemd/man/latest/systemd.device.html). Replace it with an exact-board, nonblocking systemctl restart queued from the short udev RUN action; the service owns the delay. Limit the usb_role rule to the intended controller and use exact NUL-separated matching in both rules. Repeated requests can restart the settling window, and start-rate limiting is disabled for this event-driven oneshot; each invocation has a 10-second timeout. [Linux v6.19 role-switch source](https://github.com/torvalds/linux/blob/v6.19/drivers/usb/roles/class.c) emits KOBJ_CHANGE after a successful set. The helper avoids writing an already-host role, preventing a self-sustaining write/event cycle in the stable case. No real udev/systemd event was generated during review.

3. **Disconnect race:** recheck partner and role-file existence after the delay, and propagate failed role reads rather than writing after a failed read. Temporary fixtures reproduce the source's write after disconnect and direct invocation on EVO; repaired helpers leave those paths untouched. A disconnect between the final check and sysfs write remains a normal non-atomic kernel/userspace race; the helper cannot guarantee physical cable state.

The normal kernel owns mux policy when a consumer exists. In particular, the existing kernel patch leaves the mux unchanged when both connectors are attached, so attach order can matter; the userspace host-role write does not prove the data mux points at the short side. The source assumes fixed port numbering and that a short-side partner should use host mode; it does not classify power-only, PC or analog-audio partners or perform USB-PD policy. These limits are retained and require hardware validation, not speculative kernel changes in this installer review.

There is no new suspend/resume hook. An active gpioset process retains its GPIO request until stopped; whether mux state survives suspend, Type-C partners persist/reappear, or useful change events arrive on resume is device-dependent. The UCSI service remains a one-shot recovery. No claim is made that this fixes both-port charging/data combinations, analog headset routing or resume on either kernel.
