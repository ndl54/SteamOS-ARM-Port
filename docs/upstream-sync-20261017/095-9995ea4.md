## Findings and resolution

The three palettes are accepted byte-for-byte from source. Pulse explicitly declares the existing Steam-blue defaults. Pure Black sets both canvas gradient endpoints to #000000, retaining near-black cards/buttons. Gauges uses graphite surfaces and an amber accent. Skin IDs and titles remain unchanged; the Gauges description gains the upstream palette description. This does not make every pixel black: controls, artwork, graphs and status colours remain visible by design.

The existing backend `skins()` discovers built-ins and user overrides, filters hexadecimal colours, and returns colours through `skin_colors()` in `/state` config. `/settings` accepts a known skin ID and saves it with the existing atomic config replacement. `Ui.st -> cfg -> theme -> colour properties` supplies the shared backgrounds, cards, buttons and text; `Main.qml` replaces Ui.st when polling. The skin chooser polls state once per second while visible, so switching applies through that existing path. Shot colours override config only in the existing screenshot mode. Missing colour keys fall back to Ui defaults; all 13 palette keys in the new metadata exist. Aura still intentionally uses the default text colour. No backend, persistence, polling or screenshot behaviour was changed.

**Source-induced contrast defect repaired:** white/near-white foregrounds in active buttons, selected segments, download badges, media controls and note selections would sit on Pure Black's white accent. Gauges' amber also gives white text less than 2:1 contrast. Darkened accent fills on lit keyboard keys and the held Precise control likewise need foreground selection. Added `Ui.contrastInk(fill)`, choosing black or white by relative luminance, and derived `Ui.onAccent`. The affected consumers now select readable ink. Btn's icon and label share ink; active button and segment ink follow the actual animated fill, including the pressed state. Lit keyboard labels/hints and held Precise text use their actual darkened fill. Nonactive foregrounds retain existing theme text/dim colours. No labels, sizing, handlers, input guards, actions or state transitions were altered.

Reviewed Main, Ui, skin chooser, all four skin components, shared controls and other accent/hardcoded colour uses. Hardcoded semantic CPU/GPU/power/temperature colours, artwork overlays, launcher category colours, black-screen blanking, Bricks playfield and the home game's blue/art strip remain intentional existing surfaces; this is shared palette propagation, not removal of all fixed colours. Skin previews still share the currently selected global palette; a thumbnail is not an isolated full-theme preview. These pre-existing design limitations are recorded, not expanded into a redesign.

Compared the source parent with the fork: the bottom-screen differences were DashPage's nonzero app-ID focus guard and the thor-backlightd locked read/update fix. Both files remain byte-identical to starting main, as does the backend. DashPage's loaders, fallback to Pulse, controls, missing-stat guards and layout remain untouched. All prior 083–094 modifications outside the affected QML files are unchanged. No kernel, storage, audio, sleep, staging script or board gate is changed. Overlay installation paths were read only: the existing full dualscreen-overlay copy and QML/skins glob permissions already carry these files.
