## Findings and resolutions

1. **Fix a stale-read race introduced by follow_top.** The source reads top.current and compares top.last before acquiring the daemon lock. A concurrent dashboard apply can finish writing a newer top level between that sample and lock acquisition. follow_top then imports the old sample into the proxy and top.last, allowing the next apply to undo the dashboard level. Move the read and comparison inside the same lock used by apply. A deterministic lock-acquisition interleaving reproduced the failure on the exact merged source before the fix; the same regression passes afterward. This lock serializes daemon threads only, not external Gamescope writes.
2. **Retain upstream power-error suppression.** Identical bl_power failures log once while writes keep retrying. A successful write clears the saved error; a later failure logs again. Different error text can still produce another log.
3. **Correct outdated explanatory text.** Update daemon header and unit comments to describe the current Gamescope top-panel path and the retained direct-write proxy. All executable unit directives, ordering and exact Thor condition are identical to starting main.

Only daemon behavior and those unit comments change among product files. The tests and this report are the other additions. Every other tracked product file is unchanged against starting main, including exact `ayaneo,pocketevo` gates, UFS-bound sleep, EVO USB/MCU, Wi-Fi restore-before-scan, Android LED semantics, audio/UCM, display/Gamescope protections and collector logic. No secrets, .env or gitignore modifications occurred.
