## Actual caller and precedence

The installed common `steamos-overlay/usr/lib/steamos/gamescope-session` exports `GAMESCOPE_FORCE_INTERNAL="${GAMESCOPE_FORCE_INTERNAL:-0}"`, then launches `gamescope` with the DRM backend. The shell adds `--force-internal` only for the exact value `1`. Inherited nonempty values survive; unset and empty both become `0`. The shipped user service drop-in contains no force-internal override. An override must reach the Gamescope/session process environment; merely setting a variable in an unrelated shell is not established propagation through systemd.

main.cpp parses CLI options before this environment block. `--force-internal` sets both `g_bForceInternal` and `g_bForceInternalLocked`, so an environment value of `0` cannot defeat an explicit CLI request. Overlay-removal re-exec happens before the environment block, retaining argv and environment; the policy is established after re-exec and before backend initialization. No new live environment reread is introduced.

Previously the environment block ran only when `env_to_bool` returned true. Thus the session's default `0` left the policy unlocked; a later `GAMESCOPE_DISPLAY_FORCE_INTERNAL` X property event could set internal-only selection. The assigned source instead locks whenever the environment string is nonempty and assigns its parsed boolean, including false. The existing property handler only assigns the global and calls `GetBackend()->DirtyState()` when unlocked. With a lock, the property event cannot alter the policy or dirty the backend through this branch. Other hotplug/mode-nudge events continue to work. The handler does not rewrite/delete the X property, so the property's stored value alone is not proof of effective selection.

The property atom is interned in xwayland initialization and read by `handle_property_notify`; no other assignment bypassing these startup/property paths was found. The upstream RP6/Steam observation in the commit message is not a live Steam trace or a reproduction obtained here.

| Launch input | Effective force-internal / lock | Steam property events |
| --- | --- | --- |
| Explicit `--force-internal`, any environment | true / locked | Ignored for selection |
| Normal session, unset/empty/`0` environment | false / locked (session supplies `0`) | Ignored for selection |
| Nonempty numeric `1`, `2`, `01`, `-1`, no CLI override | true / locked | Ignored for selection |
| Nonempty `false` or `true`, no CLI override | false / locked | Ignored for selection |
| Direct binary, environment unset or empty, no CLI override | initially false / unlocked | Boolean property changes selection and dirties backend |

The existing `env_to_bool` uses `!!atoi(env)`, not a truth-string parser. Consequently even the word `true` parses as false, and malformed/overflowing numeric input is not validated by this change. Use `0` or `1` for explicit settings. The table's C++ outcomes are source/control-flow reasoning, not executed C++ tests. The updated property comment says "unset"; the actual direct-binary guard also treats an empty string as unlocked. In the normal session, empty does not provide a way to restore Steam control because the shell defaults it to `0`.

This deliberately prevents Steam's display toggle from overriding a configured session policy in either direction. A policy change requires a new process/session with the intended environment or CLI options. `0` means allow external-first selection, not force an external-only output. `GAMESCOPE_OUTPUT` remains a connector preference through `--prefer-output`, not an internal lock.

## Connector selection, hotplug and fork semantics

Reviewed current DRMBackend.cpp against report035. `drm_skip_external_connectors` returns the effective global directly; legacy ALLOW variables cannot defeat internal forcing. `setup_best_connector` requires connection, an accepted mode via `find_mode`, a CRTC from the existing chooser and a routable primary plane before ranking. Among eligible outputs an external outranks an internal, then connector priority and mode area rank within the same screen type. These fork repairs remain byte-identical.

With the default locked false value, a usable monitor can win even if Steam writes internal=true or the session prefers DSI-1. With no usable external, the panel remains eligible and can win. With explicit internal forcing, external outputs are excluded even if legacy allow variables are set; if no eligible internal remains the existing virtual/headless path is used rather than silently selecting a monitor.

`kms_device_handle_change` still marks state dirty and nudges the compositor. `PollState` calls `refresh_state` and selection; disappeared connectors are erased with the current pointer cleared, and disconnected connectors are rejected. A monitor unplug therefore permits fallback to an eligible internal/another external; reconnect permits external-first ranking again. A retained connector must still be the eligible best candidate. The compositor updates mode/EDID atoms after polling and retains its existing output resize/rotation/HDR handling. No new modes, refresh rates, leases, orientation rules or output geometry are introduced.

The route check is static eligibility, not proof of link bandwidth, format support or atomic commit success. It checks the chooser's first CRTC, without searching alternative routes. Existing allocation/error propagation and atomic retry limitations remain. If there is no eligible output, logical headless selection does not submit a disabling atomic commit; a still-connected but policy-excluded output may retain its last scanout until another modeset. Cached raw touch connector pointers are not re-associated on connector removal; USB/MST touch lifetime concerns from 035 remain unresolved. These are inherited boundaries, not regressions repaired by the policy lock.

The internal-only shader dimming assignment in `update_color_mgmt` remains intact: external connectors get unity software backlight gain. The EVO internal profile/EDID gate, HDR handling, panel rotation/refresh restrictions and brightness paths are unchanged. This integration does not add monitor brightness or audio routing support.
