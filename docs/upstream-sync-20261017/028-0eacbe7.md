## Selection, callers and repairs

The source gates reboot on an exact NUL-separated DT compatible entry `lenovo,elden`. A SoC match, `lenovo,elden-extra`, TB321FU, Odin 3 and exact EVO do not enter it. `plasma` and `plasma-persistent` both set `plasma.desktop`, then default login mode `desktop`; `gamescope`, omitted or empty arguments select default login mode `game`. An invalid argument fails before changing preferences. Both Elden desktop spellings now intentionally persist the selection on ordinary writable boots, unlike the nonpersistent live `plasma` path on other boards.

The normal session wrapper is installed mode 0755 by both common and SM8750 overlay installers. The ARM hub's `open_desktop()` calls `steamos-session-select plasma` asynchronously. The hub returns success after spawning, so its response does not establish selection/reboot success. Steam's closed client/runtime call routing was not inspected; this integration does not intercept arbitrary direct manager D-Bus calls or direct `steamosctl switch-to-*` invocations.

Four semantic repairs accompany the source:

1. **Return shortcut bypass.** Existing `Return.desktop` first calls `steamosctl switch-to-game-mode`, reaching the new wrapper only if that live switch fails. A successful direct call therefore bypasses reboot and can reproduce the same in-boot display handover. Changed its Exec to `steamos-session-select --return-to-game-mode`. The wrapper normalizes that internal shortcut option to `gamescope` before the Elden branch. Outside Elden, it runs the exact original direct-switch → wrapper → qdbus fallback command, preserving EVO/other-board shortcut behavior. On Elden, a preference or reboot failure exits; it must never fall through to live switching/logout. Existing installer paths copy the same desktop file to skel, the application menu and the steamos Desktop (common install-system-fixes/vendor-apps; SM8750 direct copies). Existing installed images/custom shortcuts are not updated by this source-only review.

2. **Do not disturb the current session before reboot.** Removed `sm8550-prepare-plasma` from the new Elden branch. That helper clears Gamescope/user-manager environments, removes the runtime env file and stops portal services; if a later setter or reboot fails, upstream leaves the active session partly modified. It is unnecessary for a new boot: the installed `plasma.desktop` invokes `sm8550-startplasma`, which already performs preparation before display layout and Plasma startup. The original non-Elden case body is byte-for-byte unchanged.

3. **Respect explicit Desktop boot precedence.** Before changing preferences or rebooting into Game Mode, Elden rejects the exact whitespace-delimited `steamos.session=plasma` token and explains that a boot without it is needed. Rebooting the same forced-Desktop entry cannot honor Game Mode. Lookalikes do not trigger the guard; selecting Desktop remains allowed. This does not rewrite a bootloader, kernel command line or the init-owned SDDM snippet.

4. **Reject transient `/etc` selection.** The existing hotfix helper mounts tmpfs with source name `hotfix`, then bind-mounts its `/etc` snapshot over the live `/etc`. The new Elden guard recognizes `hotfix /etc tmpfs` in `/proc/mounts` and fails before any manager write/reboot, instructing the operator to boot with `steamos.hotfix=0`. The snapshot's root is mode 0700, so checking a child path as the desktop user would be unreliable; the mount table is used instead. A normal persistent overlay or a `/usr`-only hotfix does not trigger this guard. It does not bypass the overlay or persist anything into its underlying storage. This check is specific to the repository's hotfix implementation; arbitrary external volatile configuration layers are not detected.

The old shortcut bypass, upstream pre-failure environment preparation, ineffective Game reboot under the exact Plasma token and reboot after writes into a hotfix snapshot were reproduced using the actual shell source with mocks.

## State, authority, failure and boot lifecycle

For dependency review, read the official SteamOS Manager source at commit [`bfbb261ed6b2dda40811983caed3c9df73adac88`](https://gitlab.steamos.cloud/holo/steamos-manager/-/blob/bfbb261ed6b2dda40811983caed3c9df73adac88/steamos-manager/src/session.rs) through its read-only GitLab API. This is a pinned reference implementation, **not verification of the final image's binary/version**. Its CLI calls session-management properties over the user bus; the user manager relays SDDM writes to the privileged root manager. The session code writes defaults under `/etc/sddm.conf.d/zz-{steamos,holo}-autologin.conf`, selecting the naming convention and existing legacy file. User session preferences are also queued into `$XDG_CONFIG_HOME/steamos-manager/state.toml` (normally under the user's `.config`). That asynchronous state queue is not an end-to-end durability acknowledgement. Direct `switch-to-*` instead writes a temporary session and stops `graphical-session.target`.

The reference root manager writes the SDDM file before the setter returns; sequential CLI commands set the intended desktop before choosing desktop mode. `set -e` prevents reaching reboot after either setter fails. A partial successful setter can remain in effect if the following setter/reboot fails; this is not an atomic transaction and there is no rollback. Failure statuses propagate, the current compositor is not deliberately stopped, and the next manual reboot may use a successfully saved default. The new branch does not add root shell execution, sudo, permissive polkit rules or forced reboot flags.

`exec systemctl reboot` requests an ordinary system reboot, not a display-manager restart. Its authority and completion are separate from session preference writes: logind/polkit, inhibitors and other sessions can block or require authorization. See the [systemd logind security contract](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html#Security) and [systemctl documentation](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html). A successful request is not proof of completed hardware reboot. The exact image policies, authentication UI and shutdown behavior remain untested. Errors go to stderr; Terminal=false and the asynchronous hub do not guarantee a visible error dialog. No graphical error infrastructure is added.

The SM8750 installer only unmasks the user manager/cleanup service when the staged kernel config has `CONFIG_FTRACE=y`; unknown/prebuilt configurations remain masked. The common config requests FTRACE, but final packaging/configuration must be checked later. Missing/unavailable manager, session-bus errors, absent Plasma session and unwritable `/etc` fail through the CLI; no root-file fallback is introduced.

Boot order remains root/update recovery → early persistent `/etc` overlay → create/remove the managed `zzz-steamos-arm-session.conf` → optional RAM hotfix → collector setup → systemd/SDDM. Report 020's exact token and normal-boot cleanup are unchanged, including cleanup of a pending upper when the early overlay mount failed; mounted overlays are edited only through their merged view. A subsequent boot without the token removes the managed snippet so ordinary saved defaults can take effect. An older/different initramfs can retain it, and custom later snippets or `/etc/sddm.conf` can override the expected SDDM selection. This review does not certify arbitrary SDDM configuration precedence or repair stale configuration from other boot chains.

An `/etc` hotfix makes all subsequent `/etc` changes transient, including SDDM and the camera fragment; the new guard avoids knowingly persisting session state into it. The exact `steamos.hotfix=0` bypass must actually reach the running kernel; Elden uses a built-in forced cmdline, so merely editing a bootloader argument may not suffice. Booting a payload-free image is the other recovery route. `/usr`-only hotfixes preserve `/etc` persistence, though their arbitrary trusted payload can replace these helpers.

Source 027's Elden camera setup remains ordered before normal sessions and copies its fragment again after reboot. This is not a live WirePlumber reload/restart guarantee, nor proof that the reported display-controller jam is fixed on hardware. Report 021's upload still requires **both exact** `steamos.session=plasma` and `steamos.logupload=1` tokens. Selecting Desktop through the manager/reboot does not add those tokens or authorize upload; an already explicitly opted-in debug boot retains its requested behavior.
