## Findings and actual consumers

The changed file is `scripts/apply-overlays.sh`. Its MESA_STACK branch previously required an Android build, backed up/removed the Android Mesa package's `.so`/JSON files along with Linux packages, then installed custom Android Mesa. The source removes that requirement and Android package removal, installs only the native aarch64 and FEX x86_64/i386 Linux trees, and copies saved stock Android vendor libraries back when available. Android is also removed from the custom-Mesa version logging loop. Linux library replacement, zink session selection and MangoHud Turnip-pin removal remain unchanged.

`STOCK` is the target rootfs's `/opt/stock-steamos`, not a host directory. The old package-list loop stored originals there before replacement and retained existing backup files on subsequent runs. `scripts/build-mesa.sh` places its Android output under `usr/share/guestos/android/vendor/lib64`, including Turnip, gallium, GBM and EGL/GLES names; these match the restore destination. The new source neither requires nor copies that Android output. Its Linux output directories do not contain the Android vendor subtree in the reviewed producer. The optional Android build command remains available; it was not executed or removed.

`make-steamos-sm8650.sh` calls this overlay installer and automatically supplies MESA_STACK for `SOC=sm8550`, with explicit kernel output overrides available for EVO. The rootfs can be shared across SM8550/SM8650. This fix is selected by MESA_STACK, not a runtime board check: it protects Android for all users of this installer with the custom Linux stack. The default SM8650 path without MESA_STACK already keeps stock Android. A reused custom-stack rootfs must pass through the MESA_STACK branch to receive the backup restoration; the no-stack/MESA_SO-only branches do not restore it.

The same installer stages the common SM8650 overlay, the Android setup service, and optional `/usr/share/konkr-android` payload. `konkr-android-setup.service` invokes `/usr/bin/konkr-apk setup`; `konkr-android.service` invokes `konkr-apk daemon`. The daemon finds/downloads Steam app 3029110 (Lepton), patches its mounting/properties scripts, supplies common/versioned framework/property overlays through KONKR_LEPTON_OVERLAY and launches `lepton waitforexitandrun`. Those overlays do not replace Mesa in the tracked payload. The externally supplied Lepton binary/image and its actual guestos mounts were not inspected live; local source establishes the staging contract, not successful surfaceflinger startup. The source commit's crash explanation is upstream's stated motivation, not reproduced device evidence here.

Reviewed the separate SM8750 overlay's custom Android Mesa logic as a scope boundary. It is a different consumer, outside this 8 Gen 2/3 source; no SM8750 behavior was changed or claimed fixed.

## Remaining risks and validation boundary

No build/compile/package compilation, build-script entrypoint, rootfs/image build, VM/container startup, Android runtime, install/flash/deploy, mount, reboot/suspend, real sysfs/device access or live GPU/app test was performed.

Restoration trusts the existing stock backup. A missing, incomplete, stale or previously contaminated backup cannot establish a complete matching Valve stack; copying overlays files and does not delete arbitrary extra custom libraries. Fresh roots without a backup retain their existing Android libraries. Permission/ownership fidelity and actual Valve package manifests were not validated against a real image; mocks do not prove those properties. The normal prior installer did create the destination and back up matched package files, but recovery from a damaged rootfs is not guaranteed.

Actual surfaceflinger/Lepton startup, A740/A750 GPU compatibility, Android app rendering and repeat launches remain unverified on hardware. The compiled kernel Binder configuration and final image's library contents also remain future build/device checks. Existing other-board, display, sleep, audio and collector validation risks remain open.
