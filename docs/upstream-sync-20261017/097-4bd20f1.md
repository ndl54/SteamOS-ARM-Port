## Volume path and conflict resolution

The source intends to leave the DMG input0 mouse interface outside this composite and read its `EV_REL/REL_WHEEL` directly in the shared volume helper. The unchanged input1 JP map still forwards `KEY_VOLUMEUP/DOWN` to the virtual keyboard; ordinary gpio/InputPlumber keyboard volume inputs retain their path.

The upstream helper accepted any name containing `ayaneo device` on every board, without VID/PID or interface identity, and its event branch treated REL_WHEEL on any watched fd as volume. That broadens a shared service beyond the DMG-specific feature and could change EVO/other-board behavior for matching input devices. Repair:

- Require the exact NUL-delimited DT compatible token `ayaneo,pocketdmg` before considering a wheel.
- Additionally require the AYANEO DEVICE name, sysfs vendor `1c4f`, product `0002`, phys suffix `/input0`, and the REL_WHEEL capability bit. Missing/unreadable identity or capabilities fail closed. Name matching alone is insufficient.
- Store each opened fd's role alongside its path. Only wheel fds handle REL_WHEEL; ordinary key fds retain only the existing key path. Wheel KEY events and non-wheel REL events are ignored.
- Keep the full 089 lifecycle in the conflict: release-before-repeat ordering, current-key ioctl, duplicate press/repeat suppression, EOF/error cleanup, EAGAIN handling, suspend close/reopen, hotplug scan, safe timing and concrete-sink audio operations. Place the wheel branch **after** SYN_DROPPED/desynchronization handling so discarded events cannot adjust volume.
- Wheel input stays one-shot: positive -> volume up, negative -> down, zero ignored. It neither starts a key hold nor changes an independent held key's timer. Its fd role is removed/rebuilt through the same drop/hotplug/resume path. The internal `open_devices` tuple now includes that role; its only production caller is this helper.

The source's bounded policy of one configured step per nonzero REL_WHEEL packet is retained, regardless of magnitude. REL_WHEEL_HI_RES and horizontal scrolling are ignored. This avoids double-counting a normal wheel packet plus its high-resolution companion, but accumulated detents in one packet are not expanded; physical wheel resolution/direction and desirable fast-scroll behavior remain unverified.

The helper does not exclusively grab the mouse, preserving its existing no-grab policy. This composite's exclusion does not prove that some other installed/user composite or consumer cannot grab or also process it. Desktop scrolling alongside volume, input permissions and duplicate user-session consumers remain runtime questions.
