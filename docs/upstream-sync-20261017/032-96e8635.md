## Focus transition and dependency contract

`wlserver_keyboardfocus` requires the existing Wayland lock. It first deactivates the previous XDG toplevel when changing surfaces, and activates a new XDG toplevel only for a non-null new surface. The new branch then handles null: notify keyboard focus clearing, set Gamescope's cached `kb_focus_surface` to null, optionally release the cursor constraint, and return before virtual-keyboard selection or either `notify_enter` call. An already-null request still reaches the clear notification, so it can reconcile a seat whose focus differs from the cached pointer.

For a valid surface, the existing virtual keyboard selection, keycode/modifier snapshot, enter notification and constraint lookup remain byte-for-byte unchanged. A missing virtual keyboard on a valid-focus path still asserts; this patch does not hide initialization failures or allow a null seat/display. Initialization creates the seat before starting input backends. Normal shutdown stops the Wayland/compositor activity before destroying display clients.

The local Meson dependency is `wlroots-0.20` (>=0.20.0, <0.21.0). The build script, read but not executed, forces the wlroots fallback and pins Valve Gamescope `ad2763da1c48860f649abfe842a087188dcb6e20`. A read-only GitHub contents API lookup resolved that submodule to wlroots `d783533489e1f75d6886c2ab5c5960090ef268f8`. Fetched and inspected the pinned [seat keyboard implementation](https://gitlab.freedesktop.org/wlroots/wlroots/-/raw/d783533489e1f75d6886c2ab5c5960090ef268f8/types/seat/wlr_seat_keyboard.c); content SHA-256 was `a19a9af3686bff2c3eca0bd999eb3bd5a6e9654c5706fd8b91f3b33dfb1142a7`. This is remote dependency source evidence, not the installed library or a built binary.

The pinned `notify_enter` explicitly asserts a non-null surface. `notify_clear_focus` delegates to the current grab's `clear_focus` callback. The default callback clears through the lower-level enter-with-null path, sending leave to the previous client, removing its surface-destroy listener and clearing the seat focus. Actual surface destruction also clears the seat through its own listener. The [official API documentation](https://wlroots.pages.freedesktop.org/wlroots/wlr/types/wlr_seat.h.html#wlr_seat_keyboard_notify_clear_focus) confirms grab-aware clearing. The new call does not end/cancel a grab or bypass its policy: a non-default grab may handle clearing differently. No application-installed seat keyboard grab was found in the reviewed Gamescope source. Nested backend keyboard capture is a separate mechanism and is unchanged.

## Callers, lifetime and locking

1. `wlserver_handle_key` temporarily redirects volume/power keys to server 0 when a root input surface exists, then restores `old_kb_surf` using `bConstrain=false`. The old pointer can legitimately be null. Previously this called `notify_enter(nullptr)`; now the root receives the key and the restore requests a leave. Both temporary transitions preserve pointer constraints. This is a concrete source-level null path, not a reproduced sleep/wake failure.
2. Global compositor focus selection in `steamcompmgr.cpp` checks `win_surface` before calling and rechecks inside the Wayland lock. It therefore normally skips the call when no main surface exists. This patch does not change that policy to clear focus on every no-window transition.
3. `handle_wl_surface_id` resolves association under the lock, checks `current_surface`, then uses `main_surface` for keyboard focus. An override can supply a current surface before the main surface exists; the keyboard call is now null-safe. The adjacent mouse-focus path is unchanged and is not certified null-safe by this keyboard-only review.

`wlserver_run` holds the Wayland mutex across event dispatch, including input and surface callbacks; compositor-side callers explicitly lock. The null branch neither reacquires nor releases that lock. Callers still unlock/flush after return, and the dispatch loop can continue. There is no new wait, retry, queue, thread, synthetic key, service action or compositor nudge. The assertion helper uses trylock to detect a busy mutex, not thread-owner identity; correctness still depends on the actual caller locking discipline reviewed here.

X11 association teardown clears main/override surface links under the lock. `handle_wl_surface_destroy` clears Gamescope's cached keyboard/mouse surface pointers before releasing surface metadata. XDG/layer teardown similarly clears matching cached focus pointers and nulls association state; XDG unmap marks the window unmapped/dirty. The compositor retains XDG window references while its dirty pass clears/reselects focus. None of these lifetimes is strengthened by a null check. In particular the function accesses the previous non-null cached surface before its new guard, and a non-null dangling argument remains invalid. The locally saved surface during temporary key routing is protected against ordinary concurrent event-loop teardown by the lock, not by acquiring a new surface reference; reentrant/custom-grab behavior still needs runtime validation.

The existing X11 window/global focus cache invalidation and XDG unmap/focus repicking are unchanged. No claim is made that every window-destruction, stale window pointer, Xwayland restart or no-candidate transition is repaired. This integration addresses the explicit null-surface API misuse, not general ownership recovery.

## Modifiers, constraints and event progress

Clearing focus does not reset physical keyboard/XKB state, pressed-key/hotkey bookkeeping or IME timers. It avoids switching the seat to the virtual keyboard merely to leave a surface. In the temporary physical-key route, the active keyboard may therefore remain the physical group after restoring null; the next key/modifier handler still selects its correct keyboard, and a subsequent valid focus uses the unchanged virtual-keyboard enter path. No fabricated releases or modifier reset are added. Held-key/modifier behavior across physical, virtual and IME switching remains a runtime validation item; the inherited virtual-keyboard snapshot is not proof of physical-key restoration correctness.

With `bConstrain=true`, `wlserver_constrain_cursor(nullptr)` deactivates an existing constraint, applies its optional cursor hint, clears the stored constraint and confinement region, and returns. Its no-constraint case is a no-op. The existing constraint-destroy callback also clears active state. With false, constraints intentionally survive the temporary focus round trip. This separates keyboard leave from pointer capture without changing pointer focus or drag ownership. No device input was injected to test this path.

The early return prevents this particular assertion from terminating Game Mode; it adds no blocking work and leaves ordinary dispatch/flush behavior intact. It does not restore a missing window or Xwayland server, repair DRM wake/page-flip failures, or guarantee resumed frame/input progress. The source's wake description is an upstream observation, not hardware evidence obtained here.
