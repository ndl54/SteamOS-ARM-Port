## Findings and resolutions

1. **Accepted source intent:** normal main-window close is refused while busy; the modal progress dialog cannot be dismissed with a normal delete event. The pulse timer and dialog are removed only when the worker's result reaches the main loop. Confirmation can still be cancelled before starting. There is deliberately no mid-write cancellation button.
2. **Exception path could trap the UI indefinitely:** source called `_pkexec` without catching launch/decoding failures, and thread creation failure also left busy set. Added `run_install` with explicit failure results and centralized completion; thread-start failure releases the progress dialog and busy state. Probe thread-start failure is handled too because the new close guard also applies during probing. A launch/log exception never produces success.
3. **Output ownership and log persistence:** install stdout/stderr now share a private mode-0600, uniquely named temporary file instead of separate in-memory pipes. `subprocess.run` still waits for the child. A GTK window close cannot break an install-output pipe or produce UI-related SIGPIPE; large rsync output is not accumulated in RAM. Only the last 8,000 bytes are decoded with replacement for the GUI, followed by the full-log path. The log survives app closure, but temporary-storage policy may remove it at reboot. No log is uploaded. Probe output remains separately captured and decoded with replacement.
4. **No terminal for sudo fallback:** use `sudo -n --` and DEVNULL stdin; a missing graphical auth helper must fail visibly instead of waiting for an unseen password prompt. Polkit remains interactive via its authentication agent. Nonzero exits, including authentication denial/cancellation codes and signal-derived codes, are shown as failures. Success requires exit zero.
5. **Cleanup could falsely report success:** the actual shell installer previously suppressed every unmount failure, cleared all tracking, and printed `done`. Cleanup now attempts mounts in reverse order, reports failures, keeps failed mounts for the EXIT retry, and returns nonzero. The EXIT handler preserves an existing failure code or converts cleanup failure into exit 1. Explicit final cleanup failure prevents the success message even if the subsequent EXIT retry succeeds. No directory removal or new disk operation was added.
6. **Progress text/layout:** removed the unverified 5–10 minute promise (copying games can take much longer), mentions authorization, and bounds label width for wrapping. This is still an indeterminate pulse, not measured progress.

## Remaining risks and evidence boundary

These are source and isolated host-mock results. No real GTK display, polkit agent, sudo authentication, device installation, Linux mount cleanup or boot has been exercised. Real window-manager placement, narrow-screen layout, authentication-dialog stacking and tablet/handheld behavior need later device validation.

The normal GTK close path is guarded. This is not a supervisor that survives desktop-session loss, a GUI crash, forced process kill or power loss: a privileged child may survive abrupt GUI termination, and forced power loss can leave a partial install. No claim of protection against those events is made. A genuinely stalled installer keeps the indeterminate window open; there is no destructive timeout/cancel. Full temporary logs consume local space and must be saved before reboot if needed. Root/GUI environmental overrides and legacy CLI behavior are inherited, not redesigned here.

No build, compiler, package compilation, VM/container startup, real installer (including dry-run), pkexec/sudo UI, disk tool, mount, resize, format, flash, deploy, reboot or live log upload was run. Global build and device/runtime validation remain deferred by the 109-source protocol.
