### Fixed: BusyBox does not force a block device through a loop with `mount -o loop`

The initramfs installs BusyBox applets into `/bin` and uses only that PATH. [BusyBox mount source](https://raw.githubusercontent.com/mirror/busybox/1_36_stable/util-linux/mount.c) ignores the loop option and automatically attaches a loop only for a regular file, not a block device. Retrying the same super block device with the source's `-o loop` therefore does not implement its intended sector-size workaround.

Keep the normal direct mount first. On failure, explicitly find and attach a loop with the [BusyBox-compatible losetup interface](https://raw.githubusercontent.com/mirror/busybox/1_36_stable/util-linux/losetup.c), then mount that loop. Failed mounting detaches the newly allocated loop. Successful mounting requests lazy detach/autoclear, allowing it to remain mounted for logging and be released on last close; see the [Linux loop driver's LOOP_CLR_FD implementation](https://raw.githubusercontent.com/torvalds/linux/v6.19/drivers/block/loop.c). No util-linux-only `losetup --show` option is used in early boot.

Explicitly request `CONFIG_BLK_DEV_LOOP=y` in both the normal TB321FU fragment and optional 7.2.6 wrapper. The initramfs cannot load a loop module before mounting root. Final Kconfig and the actual BusyBox binary/applets still require later image validation.

The Gen 3 fstab retains the source's explicit `/dev/disk/by-partlabel/super`, `loop` option and zero fsck pass. Both base and upper fstab are updated. Gen 4 still has no super mount. The later rootfs uses its own mount utility; [util-linux 2.40 loop setup](https://raw.githubusercontent.com/util-linux/util-linux/v2.40/libmount/src/hook_loopdev.c) supports reuse of a matching existing loop to avoid overlapping mappings. Actual rootfs utility versions and early-logger/systemd handover were not exercised here.

### Fixed: preserve an activatable home.mount and update both etc layers

The source masks only lower `/etc/systemd/system/home.mount`. An existing unit in the persistent upper layer hides that mask. Masking also makes home.mount unavailable to units requiring it; the repository's `sm8350-overlay/etc/systemd/system/home.mount` already documents and handles that SteamOS dependency for another userdata-root layout.

Use that existing self-bind unit design for both tablets: `/home` remains a directory on userdata, and `home.mount` binds it onto itself without waiting for the Deck partition. Write the replacement into base `/etc` and an existing upper layer, creating the unit directories and unlinking an old mask before writing. The home-expansion stamp remains. No normal handheld home layout is changed. This is a source-level dependency repair; systemd activation was not tested on this macOS host.

### Fixed: FAST could skip patches on a fresh cache

Read the complete [pinned external builder](https://github.com/enij90/armada-tb321fu/blob/1cfa907237d190c03db9392cd858de2208eb7892/packages/kernel/scripts/build-kernel.sh). Any nonempty FAST skips patch application and defconfig, even when the earlier extraction branch has created a fresh source tree. Thus both FAST=1 with no prepared tree and FAST=0 forwarded literally are unsafe.

The wrapper now accepts only 0/1, converts 0/unset to empty, and rejects FAST=1 unless the 7.2.6 cache contains a nonempty .config, before cleaning outputs or starting a container. The pinned builder still recopies DTS files and re-merges the fragment during reuse. The cache must belong to this pinned recipe; the .config check is not a cryptographic provenance check or protection against arbitrary cache corruption.
