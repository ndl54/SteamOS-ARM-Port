### Clock ceiling is not a forced SDR50 capability

Inspected pinned `drivers/mmc/core/host.c`, `core/core.c`, `core/sd.c`, `host/sdhci.c`, `host/sdhci.h`, `host/sdhci-msm.c` and MMC/SDHCI bindings. `mmc_of_parse()` reads max-frequency into f_max; SDHCI retains a lower supplied maximum; `mmc_set_clock()` caps requested clock at f_max. The MSM clock path programs GCC according to bus mode. This is source control-flow evidence, not a measured clock.

Neither the inherited SoC nor board SD node removes SDR104 capability. SDHCI derives modes from capability registers (optionally masked/overridden by DT); SD core selects SDR104 first when host and card both support it, independently of f_max. Thus a100 MHz cap can still negotiate **SDR104 at100 MHz**, rather than SDR50. The source subject and original comment overstated this. Retained the narrowly scoped frequency workaround and corrected the include comment; did not invent unverified hardware capability masks or force SDR50.

The pinned `sdhci_msm_is_tuning_needed()` skips SDR104/HS200/HS400 DLL tuning at host clock <=100 MHz. However, its preceding SDR50 + `SDHCI_SDR50_NEEDS_TUNING` branch returns true regardless of that threshold. Therefore “the controller never tunes at100 MHz and below” is not universally true. The include and report now state this exception. Actual negotiated timing, register capabilities, clock rounding and card stability remain hardware questions.

## Installer status repair

Upstream wraps the entire Action invocation and output filter with `|| true`, suppressing target validation, lock, backup, write, flush and readback errors as well as reboot disconnects. It would then print Done. That cannot safely distinguish a rebooting tablet from an earlier failed write.

Added a narrowly scoped `action.sh --no-reboot` mode. Unknown/extra arguments fail before lock acquisition. The no-argument KernelSU Action still executes the existing checks/writes and requests reboot. The host invokes the no-reboot mode and requires successful remote exit, including lock cleanup, before issuing a **separate** reboot command. The complete Action body from D initialization through final sync is byte-identical to starting main: exact board/active-A/target/backup/lock/prewrite/flush/readback guards are preserved, not bypassed or claimed newly fixed. The existing known shared hash-helper limitation remains below.

After checked preparation:

- A zero reboot command status says only that the command returned successfully; SteamOS boot is explicitly unverified.
- A nonzero status is reported as **reboot request unconfirmed**, with the original ADB status/output and advice to check the tablet before retrying. Exit2 represents this uncertainty; it does not call the verified write failed or falsely report reboot success. A permission error and a reboot-related transport loss cannot reliably be distinguished from this single ADB result, so neither is silently accepted.
- ERR suppression exists only inside a subshell for that separately handled reboot request. The normal host ERR trap remains active for preparation, earlier stages and cleanup. This scope avoids inherited Bash3.2 ERR diagnostics falsely labelling the known ambiguous reboot result as an installer/write failure. Direct executable dispatch retains the resolved ADB path and explicit selected serial.
- Stage-only mode still prints Done for staging, without running Action/reboot. Both existing switch spellings remain accepted. There is no reconnect, automatic retry, device retargeting or boot-completion claim.

Except for an exit-status documentation comment, the host installer before its final lock-release/switch block is byte-identical to starting main. This preserves100's resolved executable/command dispatch, all six pushes/seven source paths, WSL conversions, explicit serial, binary output, CRLF/status handling, argv-safe ZIP expression and cleanup. The entire101 CARD body and its diagnostics, digest validation, owned mount cleanup/status propagation are unchanged. `storage.sh` is unchanged. `mk-gen5-test.sh` already copies both this installer and the complete Action module; it needs no new packaging dependency and was not run.
