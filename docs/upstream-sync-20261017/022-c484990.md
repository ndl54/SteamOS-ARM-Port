## Execution path and review findings

`main.cpp` already calls `wlserver_init()` before `init_pipewire()`. However, the compositor thread and `wlserver_run()` come **after** PipeWire initialization. Consequently the old indefinite `pw_loop_iterate(..., -1)` node-ID wait can keep the Wayland event loop and compositor from running. A false return merely prints a capture warning; it does not abort Gamescope startup. The upstream Y700 Gen 4 black-screen observation is upstream evidence, not a reproduction in this review.

The build script stages this vendored source and explicitly enables PipeWire. It was read, never executed. `get_time_in_nanos()` in `steamcompmgr.cpp` uses CLOCK_MONOTONIC; no compositor-thread initialization is required to call it. The source's new forward declaration matches the existing definition and declaration. The project uses C++20.

The original source gives initialization a five-second deadline and 100 ms loop waits, then transfers loop processing to the existing detached PipeWire worker even if no node ID has arrived. PAUSED publishes the stream node; STREAMING enables capture. ERROR/UNCONNECTED set `running=false`. There is no condition variable here: the wait is loop iteration/polling plus callback state checks.

The textual merge alone leaves three relevant problems: the initial wait ignores `running=false`; delayed node publication races with the Wayland reader because the node field is a plain integer; and failed initialization leaks partially created objects and the nudge pipe. The source's unconditional claim that screen capture will come up later is also too strong for current clients.

## Integration repairs

1. Preserve the five-second monotonic deadline and asynchronous continuation. Each iterate timeout is the smaller of 100 ms and the remaining duration rounded up to milliseconds. No new full 100 ms wait starts at the deadline. `-EINTR` retries against the same deadline; other negative results are failures. This bounds deliberate waiting, not callback execution, scheduler stalls, synchronous setup operations or teardown. Rounding can add less than 1 ms; it is not a hard real-time five-second guarantee.
2. Check `state->running` in the wait predicate and after leaving the loop. Set it before `pw_stream_connect`, so a synchronous terminal callback cannot be overwritten with true afterward. Terminal startup state returns false promptly; no dead worker is launched. Terminal callbacks clear `streaming` and invalidate the node ID.
3. Make `stream_node_id` an atomic uint32_t and include `<atomic>` explicitly in its header. Delayed callback publication and Wayland reads now use atomic access. The variadic node log explicitly calls `.load()`, avoiding passing an atomic object to `%u`. No new cross-thread access to `running` is introduced: callbacks execute on the initial loop owner, then on the worker after handoff; the main thread stops reading it before constructing the worker.
4. Add one initialization-only failure cleanup path for failures after pipe allocation: destroy stream, disconnect core, destroy context and loop, null object pointers, close/reset both pipe descriptors, and clear capture state. Iteration failures leave the loop before cleanup. This runs before either the PipeWire worker or compositor thread exists, so it does not race a compositor-held capture buffer. A failed pipe creation has no acquired resources and still returns directly. A nudge with no valid write descriptor becomes a no-op, avoiding repeated EBADF messages after initialization failure.
5. Correct the startup-order comment and timeout diagnostic. Timeout retains the live connection and starts the worker; it is not a disconnect or a teardown. The message states that capture clients may need to reconnect.

## Late capture, ownership and remaining lifecycle limits

`gamescope_pipewire_bind()` sends the current node ID once. The private protocol promises that event by the roundtrip following bind; no later broadcast/subscriber registry exists. A client binding during the deferred interval can therefore receive SPA_ID_INVALID. A later client/rebind can obtain the newly published valid node, but this change does not promise that every existing capture client automatically recovers. Changing the protocol or all external consumers is outside this source's startup fix. The timeout log now reflects the limitation.

The initial main-thread `pw_loop_enter`/iterate/leave completes before worker construction. The worker is the next loop owner; no two threads iterate concurrently. These enter/leave calls are ownership markers, not a new general mutex around the stream. The existing worker polls PipeWire and the nudge pipe, drives callbacks, and tears down stream/core/context/loop after terminal state, poll hangup or iterate failure. This worker body is byte-preserved. There is no automatic new `pw_context_connect` after terminal failure, so a daemon restart is not guaranteed to restore capture. A server that never completes negotiation may leave the background worker waiting, while Gamescope's main startup proceeds.

Existing runtime capture ownership uses atomic pending-buffer exchanges, `streaming`, and buffer pointer publication, but `request_buffer()` still accesses the stream from the compositor while worker teardown has no shared lifetime mutex/join protocol. The detached worker has no normal-exit join, and its nudge pipe is not closed by its existing teardown. These pre-existing runtime-disconnect/shutdown limitations are **not certified safe** by this review and are not solved by atomic node publication. The new cleanup is deliberately confined to the pre-thread initialization failure path; normal runtime buffer lifecycle is unchanged. The final validation should exercise disconnect during active capture as well as delayed startup.

Reference cross-checks used official [PipeWire loop documentation](https://docs.pipewire.org/group__pw__loop.html), [SPA loop control source documentation](https://docs.pipewire.org/spa_2include_2spa_2support_2loop_8h_source.html), and [stream documentation](https://docs.pipewire.org/group__pw__stream.html). In particular, SPA describes entering/leaving the thread that iterates the loop. These current online API references are not evidence of the exact library binary installed in the eventual rootfs.
