## Findings and resolutions

### Preserve explicit settings instead of inferring ownership from age

The upstream startup loop writes false to every profile before creating its marker. There is no evidence identifying an existing true value as a shipped default rather than a deliberate user choice. Reproduced with the exact source fragment: a user's AC=true became false. This conflicts with the required custom-settings preservation.

The merged helper now reads each value as a string twice with different fallback defaults. Matching returned values mean the entry exists and are left alone, including true, false, empty and unfamiliar strings; there is no sentinel collision. Only a missing key, yielding the two fallback values, is seeded false. KConfig's cascading defaults are respected, so an inherited false needs no user-file write. Explicit inherited true is also preserved. A differing result inconsistent with the missing-key pattern defers the operation rather than guessing.

The original config-home marker path and v1 name are retained. After successful completion, subsequent starts do no reads/writes, so later user changes remain effective. A pre-existing marker from an upstream installation is respected; this cannot reconstruct choices already overwritten by that older implementation.

The staging producer also unconditionally replaced an existing home powerdevilrc. It now seeds that file only when neither a filesystem entry nor a symlink exists. Existing files and dangling symlinks are preserved. System/skel defaults continue to be installed as before. This change is restricted to powerdevilrc; it is not a general redesign of image-install preservation.

### Do not mark failed migration as completed

Upstream discards every writer failure with `|| true` and still creates the marker. Reproduced with a failed Battery write: Battery remained absent, but the marker prevented retry.

The merged implementation requires both KDE tools, stops on read/write failure, verifies a written value by reading it back, and creates the marker only after every profile has been handled. A partial run leaves successfully seeded profiles intact and retries the rest; any user choice made between attempts is preserved. Marker creation failure logs a retry message and returns successfully so it does not block the caller's Desktop switch.

The official pinned [kreadconfig implementation](https://raw.githubusercontent.com/KDE/kconfig/4c0c790c2da02cd7bedb65564cc22f1dce4c71ba/src/kreadconfig/kreadconfig.cpp) prints string values/fallbacks; boolean mode instead encodes the boolean in the exit status and is deliberately not used. [KConfig flags](https://raw.githubusercontent.com/KDE/kconfig/4c0c790c2da02cd7bedb65564cc22f1dce4c71ba/src/core/kconfig.h) distinguish cascading defaults from global config. The pinned [kwriteconfig implementation](https://raw.githubusercontent.com/KDE/kconfig/4c0c790c2da02cd7bedb65564cc22f1dce4c71ba/src/kreadconfig/kwriteconfig.cpp) rejects immutable/unwritable entries but does not propagate the result of sync, motivating readback. These are reference-source observations, not tests of installed KDE commands.

## Remaining risks and boundary

Explicit old true values are intentionally preserved because their origin cannot be proven; those desktops may still encounter the reported idle failure until the user disables screen-off. Missing KDE tools prevent seeding on paths without system defaults. Existing v1 markers suppress reprocessing, including markers from a previously failed upstream migration. An immutable, inaccessible, malformed or unsupported real KConfig file may behave differently from the mock; actual KDE packaging, config cascading and startup/reload timing need image/runtime validation. Readback is not fsync-backed durability. Reads, writes and marker creation are not one locked transaction; a simultaneous settings editor or preparation process can race them. No attempt is made to roll back already seeded keys after a later failure.

Keeping the panel on can increase idle power use. Manual screen-off, explicit user re-enabling, suspend/resume and independent compositor/driver failures remain outside this prevention. No claim of DSI recovery, successful suspend/resume or physical input/display behavior follows from these checks.
